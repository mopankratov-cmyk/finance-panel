# Модуль «Деньги (ДДС)»: правила для любого исполнителя

> Разделы `/calendar`, `/payments`, `/accounts`, `/loans` и их роуты `/api/finance/*`, `/api/opiu/*`.
> Читать до первой правки в этих папках — вместе с `docs/PROJECT-KNOWLEDGE.md` (§5 «Честность данных»).

## Зачем этот файл

Разбор модуля 03.09.2026 показал не «баги в коде», а один способ их появления: задачи ставились
исполнителю (Codex) как последовательность шагов, без общей модели. Исполнитель делает ровно
шаг — и в коде появляются **четыре списка статей** (формы, выписка, очередь, свод), **четыре
сопоставителя** план↔факт с собственными списками занятых фактов, **две таблицы счетов**
(`accounts` и `finance_accounts`), **три реализации P&L**. Каждая правка была верной сама по
себе; вместе они друг о друге не знали.

Лечится не более подробными шагами, а обратным: в задание вносятся **инварианты, которые нельзя
нарушать**, точные файлы-источники правды и проверка на выходе. Этот файл — и есть та модель.
Задача исполнителю ссылается на номера правил из §2; тест-сторож в `lib/finance/*.test.mts`
держит правило, когда автор задачи уже забыл.

## 1. Источники правды — один на сущность

| Сущность | Где | Правило |
|---|---|---|
| Статьи ДДС и их разделы | `lib/finance/categories.ts` | Единственный список. Новая статья = строка в `REGISTRY` + раздел. Формы — только через `categoryOptions(current)`. Литералы статей в коде запрещены; константы `LOAN_CATEGORIES`, `TRANSFER_CATEGORIES`, `INTERCOMPANY_LOAN_CATEGORIES`. `PAYMENT_CATEGORIES` в `lib/constants.ts` — алиас, deprecated. |
| Счета | таблица `accounts` (`lib/finance/dbServer.ts`) | `finance_accounts` / `finance_payments` — зеркало для Telegram-бота, наполняется `/api/opiu/sync` как побочный эффект открытия календаря. Валидировать по зеркалу нельзя. (Известный долг: `calendar-publish` и `browser-payout-snapshots` пока делают именно это.) |
| Платежи | таблица `payments`, тип `Payment` в `lib/types.ts` | `status ∈ planned / done / cancelled`; знак `amount` = направление; `comment` несёт служебные метки (§3). `import_source` уникален — ключ идемпотентности импорта. |
| Связь план → факт | `lib/finance/factLinks.ts` | `consumedFactIds()` — все факты, уже занятые какой-либо меткой. Любой новый сопоставитель обязан её вызывать. |
| Замена части календаря | `components/calendar/calendarReplace.ts` | Одна функция и для числа в подтверждении, и для удаления. |
| Раздел ДДС для свода | `sectionForCategory()` из справочника | `ddsSummary.ts` только реэкспортирует. |
| Распознавание договора | `lib/loans/recognizeLoan.ts` (+ `aiRecognition.ts`, `schedule.ts`, `exchangeRate.ts`) | Единственный путь: файл → условия + график + курс + подсказка компании/счёта. |
| Распознавание выписки | `lib/finance/bankStatementServer.ts` (+ `xlsxGrid.ts`, `bankStatementGrid.ts`, `bankStatementPdf.ts`) | XLSX детерминированно, PDF через ИИ; классификация с данными из базы. Первый лист — по `workbook.xml`. |

## 2. Инварианты

- **I1. Один факт — одно обязательство.** Факт ДДС, на который уже ссылается `[calendar-fact:]` или `[paid-by:]`, не предлагается ни календарю, ни сверке кредитов, ни зарплате. Проверка: `consumedFactIds(payments)`. Сторож: `lib/finance/planFactExclusive.test.mts`.
- **I2. Автозакрытие — только при точной сумме.** План закрывается фактом без подтверждения только если суммы совпадают (±1%). Расхождение по сумме — всегда ручное подтверждение, сколько бы баллов ни набрали компания/кошелёк/контрагент. Сторож: тот же файл.
- **I3. Открытие страницы не меняет данные.** Код не двигает даты, статусы и суммы платежей при монтировании компонента. Всякая мутация — за действием человека. Исключение на сегодня — валютный пересчёт графиков (`components/loans/currencyRefresh.ts`), решение по нему за владельцем (§6).
- **I4. Ноль ≠ «не посчитано».** Нет данных — `null` / прочерк / плашка «не считается». Сторож для `/pnl`: `lib/finance/pnlHonesty.test.mts`.
- **I5. Разрушительная операция говорит точно, что удалит.** Число в подтверждении считается той же функцией, что удаляет. Диалог не обещает того, чего код не гарантирует.
- **I6. Провал записи виден.** `FinanceProvider.persistError` → баннер в `AppLayout`. Новые пути записи мимо `dispatch` обязаны показывать ошибку пользователю, а не `console.error`.
- **I7. Компания и кошелёк — по id, не по имени.** Между очередью, импортом и календарём передаётся `companyId`. Эвристика без якоря (пустой владелец выписки, два подходящих кошелька, одна похожая операция) → «не знаю» + `needsReview`, а не первый элемент списка. Сторож: `lib/opiu/bankOwnerGuess.test.mts`.
- **I8. Служебные метки в `comment` не стираются формами.** Календарь — `commentWithPreservedMetadata`; кредиты — `preservedLoanMarkers`; реестр — `PaymentForm` передаёт `comment` как есть. Сторож: `lib/finance/factLinks.test.mts`.
- **I9. Любая выборка, которая может превысить 1000 строк, — через `loadAllSupabasePages`.** `.limit(5000)` не помогает: PostgREST режет на 1000. (Долг: `app/api/opiu/bank-review/route.ts`.)
- **I11. Распознавание документов — только на сервере.** Договоры (`/api/opiu/loan-recognize`) и выписки (`/api/opiu/bank-statement`) разбираются в `lib/loans/*` и `lib/finance/bankStatement*`; браузер отправляет файл `FormData` и показывает ответ. Регулярок, чтения XLSX/DOCX и слияния результатов в компонентах быть не должно — иначе у разных сотрудников по одному документу выходит разное. Сторожа: `lib/loans/recognizeLoan.test.mts`, `lib/finance/xlsxGrid.test.mts`, `lib/finance/bankStatementGrid.test.mts`.
- **I10. Тест-сторож — в `lib/` или `tests/`.** `npm test` не гоняет `components/**/*.test.mts` (см. `package.json`); файл с сторожем кладём туда, где он выполнится.

## 3. Словарь меток в `comment`

Платёж хранит служебную информацию в тексте комментария. Это не идеально (см. §6), но пока так —
и стирать их нельзя.

| Метка | Кто ставит | Смысл |
|---|---|---|
| `[loan:<loanId>:receipt]` | Кредиты | получение кредита |
| `[loan:<loanId>:schedule:<rowId>:<principal|interest|penalty|fine>]` | Кредиты | часть строки графика |
| `[paid-by:<factId>]` | Сверка кредитов | строка графика закрыта фактом ДДС (статус строки → `cancelled`) |
| `[calendar-fact:<factId>]` | Календарь | план закрыт фактом (статус → `cancelled`) |
| `[priority:A|B|C]` | Календарь | приоритет платежа; без метки — подсказка по статье (`getPaymentPriority`) |
| `[original-due:YYYY-MM-DD]` | Перенос просрочки | исходная дата до переноса |
| `[overdue-calendar-date:YYYY-MM-DD]` | Очередь просрочки | дата, на которую перенесли вручную |
| `[series:<id>]` | Повторяющиеся | серия повторов |
| `[currency:] [fx-rate:] [fx-rate-current:] [fx-rate-date:] [amount-original:] [amount-currency:] [principal-original:]` | Кредиты | валюта договора и курс |
| `[annual-rate:] [monthly-rate:] [interest-frequency:] [payment-days:] [tranches:] [origination-fee:] [fee-months:]` | Кредиты | условия договора |
| `[contract:<file>] [contract-number:<№>]` | Кредиты | документ и номер договора |

## 4. Как ставить задачу исполнителю

Не «сделай шаги 1–7», а контракт. Шаблон (и готовые примеры — `docs/tz/dds-*.md`):

```
# ТЗ: <одна фраза>
## 0. Инструкция исполнителю      — зона МОЖНО, база gitea/main, бюджет попыток, когда СТОП
## 1. Цель и наблюдаемое поведение — что увидит человек на экране, не «что в коде»
## 2. Решения приняты за тебя      — всё, что можно было бы спросить, уже отвечено
## 3. Инварианты                   — номера из docs/DDS-RULES.md §2, которые задача обязана соблюсти
## 4. Зона МОЖНО / НЕЛЬЗЯ          — точные пути; всё вне зоны — стоп и отчёт
## 5. Источники правды             — какие модули использовать, какие литералы запрещены
## 6. Точки правки                 — файл : функция : что именно; сигнатуры дословно
## 7. Порядок шагов                — детерминированный, с проверкой после каждого
## 8. Что НЕ делать                — соседние «улучшения», рефакторинг, новые зависимости
## 9. Гейт                         — команды и ожидаемые числа: npm test, tsc, eslint; baseline
## 10. Стоп-условия и отчёт        — исчерпан бюджет / вышел за зону / гейт не сходится
```

Правила, из-за которых Codex «тупит», если их не написать явно:
- **Сигнатуры дословно.** Не «добавь параметр», а строка кода, которая должна получиться.
- **Baseline гейта.** Сколько тестов зелёных до задачи (`npm test` → `# pass N`). Исполнитель обязан вернуть N + свои.
- **Что считается «сделано».** Наблюдаемое поведение + тест, который это держит. Без теста-сторожа задача не закрыта.
- **Границы.** Список файлов. Зашёл в другой — стоп. Это единственная защита от «попутно улучшил».
- **Не спрашивать.** Все развилки решены в §2. Если развилка не описана — стоп и отчёт, а не выбор наугад.

### 4а. Бюджет исполнителя — что читать и когда проверять

После появления этих правил Codex начал перечитывать весь проект перед каждой задачей и гонять
полный `npm test` после каждой правки — «чтобы ничего не сломать». Это неверное прочтение: за
«не сломать» отвечают тесты-сторожа и гейт CI, а не исполнитель. Вставлять в начало **каждой**
задачи дословно:

```
Бюджет чтения: открывай ТОЛЬКО файлы из раздела «Зона МОЖНО» этой задачи
и docs/DDS-RULES.md §1–§2. Остальной проект не исследуй — за «не сломать»
отвечают тесты-сторожа и гейт, не ты.
Проверка по ходу: только тесты задачи —
  node --import tsx --test <файл теста>
Полный npm test, tsc, eslint — ОДИН раз, перед PR. Не после каждой правки.
Если для задачи нужен файл вне зоны — не открывай его, остановись и напиши.
```

Правила для того, кто ставит задачу:
- в контекст исполнителю идут §1–§2 этого файла (~50 строк) и номера инвариантов задачи, а не весь документ;
- готовые ТЗ из `docs/tz/` уже содержат зону МОЖНО и гейт — им преамбула не нужна;
- если исполнитель просит «посмотреть соседний модуль» — это сигнал, что зона задачи описана
  неполно; дописать зону, а не разрешать исследование.

Перед PR исполнитель гоняет `npm test`, `npx tsc --noEmit`, `npx eslint <файлы>`. Гейт в CI
гоняет только `npm test` — ошибку типов он пропустит в main (уже было: #804).

## 6. Что открыто — и требует решения владельца, а не исполнителя

1. **График кредита как сущность.** Сейчас график = набор платежей с метками в `comment`; остатка долга на дату нет → капитализацию процентов и допвзносы (договор Дзюбина) выразить нечем, каждый нетиповой договор вбивается руками. ТЗ: `docs/tz/dds-loan-schedule-entity.md`.
2. **Баланс счёта.** `accounts.balance` не двигается ни от одного платежа (ветка `MARK_PAYMENT_DONE` мёртвая), а весь прогноз остатка построен так, будто двигается; RUB и USD складываются. ТЗ: `docs/tz/dds-account-balance-model.md`.
3. **Зарплатная ведомость** — приедет из локальной ветки сотрудника; условия приёма: `docs/tz/dds-payroll-landing.md`.
4. Поступления, кроме МП и кредитов, невидимы в календаре (`isCalendarCashFlow`) — расходы считаются все, доходы выборочно. Нужно решение: показывать все или явно объяснить.
5. Два прогноза кассового разрыва на одном экране («Финансовый контроль» без горизонта vs сетка по фильтрам).
6. Валютный пересчёт правит и просроченные строки (I3).
7. `finance_accounts` как зеркало: `calendar-publish` не примет новый счёт, пока кто-то не откроет календарь.
8. Авто-выгрузка календаря в Google через 3 с после любой правки (`CalendarPage`, эффект на `calendarRows`).
9. `.limit(5000/20000)` в `bank-review` (I9).
10. Парсер выписки читает жёстко `sheet1.xml`; одноколоночная выписка без направления инвертирует знак.
