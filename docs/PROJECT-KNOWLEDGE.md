# Что нужно знать до первой правки

Онбординг (`docs/ONBOARDING.md`) объясняет, как настроить окружение и отправить PR.
Этот документ — про другое: про грабли, которые уже собраны, и про правила, нарушение
которых ломает данные тихо, без ошибки в консоли.

Читается за десять минут. Сэкономит дни.

---

## 1. Как устроен поток данных

```
маркетплейс (WB / Ozon API)
        ↓  app/api/sync/*      — фоновые прогоны по расписанию (vercel.json → crons)
    таблицы в Supabase
        ↓  app/api/<экран>/    — роуты читают базу, считают витрину
      экран (components/)
```

**Правило:** экран не ходит в API маркетплейса напрямую, если этого можно избежать.
Живые запросы упираются в лимиты, отваливаются по таймауту и делают экран непредсказуемым.
Всё, что можно собрать заранее, собирается фоном и кладётся в базу.

---

## 2. Кэш, который кажется кэшем, но им не является

`unstable_cache` (обёртка `loadHourlyDashboard`) **не общий между роутами** и **обнуляется
каждой выкладкой**. Ключ включает текст функции после сборки.

Из-за этого:
- справочник названий товаров то появлялся, то исчезал — жил в кэше сборки;
- остатки FBS «пропадали» после каждого деплоя.

**Правило:** справочные данные, нужные нескольким экранам, живут в таблице, а не в кэше.

**Отдельная ловушка:** если меняешь ФОРМУ данных внутри кэшируемого загрузчика — обязательно
подними версию схемы в ключе (`schema: N`). Иначе экран получит вчерашний снимок без новых
полей, а по коду будет казаться, что фича раскатана. Так уже терялись `stock_fbo` и `stock_fbs`.

## 3. WB API: что закрыто и что ломается

| Что | Правда |
|---|---|
| `GET /api/v3/orders/{id}/meta` | **Закрыт**, отвечает 405. Коды маркировки берутся пакетно: `POST /api/marketplace/v3/orders/meta`, до 100 заданий, другой префикс |
| `GET /api/v3/orders?dateFrom=` | Окно **не старше 30 суток**. На 35 — `400 IncorrectParameter`. Это была самоподдерживающаяся ловушка: без успешного прогона нет курсора, без курсора снова просится 35 дней |
| Лимиты | 300 запросов/мин на продавца. **Ответ 4XX считается за 10 запросов** — поток ошибок выжигает лимит вдесятеро и бьёт по соседним экранам |
| Повторы | Лестница повторов внутри одного запроса может занять до 85 секунд. Любой внешний бюджет надо протаскивать ВНУТРЬ запроса, иначе он не соблюдается |
| Фото | Лежит на одном из «баскетов», номер которого выводится из артикула — и иногда выводится неверно. Использовать `WbProductImage` (перебирает варианты), а не одну ссылку. У части карточек фото нет вовсе — рисуется заглушка с артикулом |

**Агентские кабинеты.** WB отдаёт сборочные задания ВСЕГО продавца, а кабинет ограничен
своими товарами. У Оптимы 92% заданий чужие. Фильтровать по товарному контуру обязательно,
иначе бюджет прогона уходит на чужое.

**Календарь площадки — московский.** Окно, посчитанное через `toISOString()`, после 21:00 по Москве
отстаёт на день: сегодняшний день WB в него не попадает. Для дат синков — `lib/sync/moscowDay.ts`.

**Прогрев ходит машиной, а не человеком.** Внутренние запросы несут `Bearer CRON_SECRET`: прокси их
пускает, но роут со своим `requireApiSession` ответит 401, и кэш не наполнится никогда. Для греющихся
GET-роутов есть `requireApiSessionOrMachine`; мутации — только с живой сессией.

## 4. Постгрес: что не работает так, как выглядит

- `date::date` по колонке **не sargable** — индекс не используется, запрос идёт последовательным чтением.
- `timestamptz → date` **не IMMUTABLE**, поэтому индекс по выражению создать нельзя (ошибка 42P17).
- Ветки `(p_cabinet is null or cabinet_id = p_cabinet)` требуют `plan_cache_mode = force_custom_plan`,
  иначе планировщик выбирает общий план и запрос деградирует.
- Один PostgREST-upsert целится в **колонки** уникального индекса. Выражение-индексы не подходят.
  Для ключей с NULL — `unique nulls not distinct`.
- **Любая выборка обрезается на тысяче строк.** Молча, без ошибки: приходит ровно 1000 строк, и код
  считает это полным ответом. `limit(50_000)` потолок не отменяет — он ограничивает сверху, а не
  снимает серверный предел. Это касается и RPC: PostgREST режет ответ функции так же, как обычный
  запрос. Читай через `loadAllSupabasePages` (`lib/supabase/loadAllPages.ts`) с обязательным
  `.order(...)` — без сортировки страницы могут перекрываться и терять строки. Помощник бросает
  исключение, если выборка превысила безопасный предел: лучше явная авария, чем тихий обрезок.
- **Апсёрт не умеет забывать.** Строка, пропавшая из ответа площадки (товар кончился, уехал со
  склада, кампания удалена), остаётся в базе с последним известным значением навсегда. Если таблица
  описывает «как сейчас», после ПОЛНОГО обхода обнуляй всё, что этим прогоном не подтвердилось,
  и обязательно сужай обнуление до контура кабинета.

## 5. Честность данных — это не стиль, это требование

Самая частая ошибка в этом проекте — показать ноль там, где правда «не знаем».

Примеры настоящих поломок:
- пустая таблица остатков давала «0 на складе» по всем товарам, хотя обход ещё не запускался;
- пустой разбор по кампаниям писал «кампаний не было», хотя реклама шла — просто разбивку не сохраняли;
- 632 пенала помечались «вывести из оборота», хотя они не маркируются вовсе;
- вкладка «Вывести из оборота» показывала ноль всегда: наполнить её было нечем, а ноль читался
  как «нарушений нет». Вкладку убрали — пустое обещание хуже отсутствия раздела;
- синк заказов при полном отбое по лимиту WB писал в журнал «ок»: зелёный журнал при пустых
  экранах не заставляет никого разбираться.

**Второе правило:** не рапортуй об успехе, когда данных не появилось. Обрезанный обход, отложенный
по лимиту сбор, неполный опрос складов — это отдельные состояния, и называть их надо словами.
Курсор при этом двигай только до того места, докуда действительно дочитал: сдвинешь дальше —
пропущенное не увидит уже никто.

**Правило:** отличай «нет данных» от «данные есть, и это ноль». Первое — прочерк и объяснение,
второе — цифра. Если объединить, пользователь примет решение по выдуманному факту.

## 6. Вёрстка таблиц

- У **закреплённой** (`sticky`) ячейки фон обязан быть **непрозрачным**. Под ней проезжают
  другие колонки, и через полупрозрачный фон их цифры читаются поверх — выглядит как наложение
  строк, а измерение геометрии ничего не показывает.
- Ячейка `colSpan` на всю ширину при горизонтальной прокрутке уезжает вместе с таблицей.
  Подпись внутри неё нужно прикреплять к левому краю.

## 7. Порядок работы

- **Миграции применяет владелец.** Пиши SQL в `supabase/migrations/`, отдавай текст — накатит он.
- **Выкладка ручная:** `npx vercel --prod --yes --archive=tgz` **только из главного рабочего дерева**.
  Из worktree команда отправит код главного дерева, и новые роуты молча не уедут.
- **Слитый PR ≠ прод.** Гейт вливает сам, выкладку запускает человек.
- **Не допушивай в открытый PR.** Гейт вливает то состояние, что увидел; второй пуш может не успеть.
  Каждая правка — отдельный PR.
- **Проверяй глазами.** Замеры врут: наложение строк было визуальным, а не геометрическим.
  Открой экран, прокрути таблицу, наведи курсор.

## 8. Что сейчас открыто

- **Складской флоу** — движение товара от приёмки на фулфилменте до списания КИЗ. Ждём описание
  от владельца, без него код писать бессмысленно.
- **Остатки FBS** — сборщик обходит по кабинету в час, данные накапливаются.
- **Возвраты** — читаются из базы, `srid` заполняется постепенно синком продаж.
