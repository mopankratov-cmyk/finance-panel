# Заявка: добавить колонку gi_id в wb_report_rows

**Кому:** Максим
**Тема:** Нужна одна колонка в Supabase, чтобы себестоимость и подготовка в ОПиУ считались
не по товару «в среднем», а по конкретной поставке — как раньше и было настроено

## Суть

У нас есть отдельная гугл-таблица **«Себестоимость поставок WB»**
(https://docs.google.com/spreadsheets/d/1LLo9jYSdXZMCvdtgFTN-e1S4FTwCM4YYyKxsrbZ6Oc4),
которую я веду вручную — в ней себестоимость и подготовка указаны **по каждой поставке
отдельно** (столбцы: номер поставки, баркод, себестоимость, подготовка). Это важно, потому
что закупочная цена товара у поставщика меняется от поставки к поставке — один и тот же
баркод в разных поставках может стоить по-разному.

Эта таблица сама по себе работает нормально — проблема не в ней, а в том, что **нечем с ней
сверяться**. Чтобы найти себестоимость конкретной проданной единицы товара по этой таблице,
нужно знать, из какой поставки она была продана — то есть нужен `gi_id` (номер поставки)
в данных о самой продаже.

Проверила напрямую через Supabase REST API:

```
GET wb_report_rows?select=gi_id
→ {"code":"42703","message":"column wb_report_rows.gi_id does not exist"}
```

Колонки `gi_id` в `wb_report_rows` нет вообще — WB Finance Report API отдаёт это поле
(`giId` в camelCase-варианте ответа), но наш синк его никогда не запрашивал и не сохранял.

Без этого поля я не могу восстановить точный расчёт себестоимости/подготовки «по поставкам» —
максимум, что доступно сейчас, это грубый фоллбэк по артикулу/баркоду без привязки к
конкретной поставке (через таблицу `product_costs`), который не различает разные закупочные
цены одного товара.

## Что нужно сделать (три шага)

1. **Добавить колонку** в `wb_report_rows`:
   ```sql
   alter table public.wb_report_rows
     add column if not exists gi_id text;
   ```

2. **Синк-job должен начать её заполнять** — в `lib/opiu/syncReportRows.ts`:
   - добавить `"giId"` в список `REPORT_FIELDS` (запрашиваем поле у WB API)
   - добавить `gi_id: text(row.gi_id)` в `reportRowForStorage`

3. **Добавить колонку в чтение** — в `lib/opiu/reportRows.ts`, в список `REPORT_COLUMNS`
   добавить `"gi_id"`.

## Важный нюанс: старые данные — нужен пересинк

Так же, как было с `cashback_discount`: колонка останется пустой для уже засинканных
периодов, пока их не пересинкать. Прошу пересинкать **только прошлую неделю**
(последнюю полную неделю перед сегодня, уточни точные границы по нашему недельному циклу
ОПиУ, обычно пн-вс) — этого хватит, чтобы проверить механизм сверки на реальных данных, а
на всю историю пересинк не нужен.

Напоминаю (по опыту прошлого раза): пересинк периода перезаписывает **всю строку целиком**,
не только `gi_id` — это ожидаемо и не должно быть разрушительно, но стоит рассчитывать
нагрузку на лимиты WB API соответственно.

## Что уже готово с моей стороны

Код в `lib/opiu/metrics.ts` и `lib/opiu/buildReport.ts` уже восстановлен и умеет искать
себестоимость/подготовку сначала по паре (`gi_id` + `barcode`) через отдельный источник
(гугл-таблица поставок), с фоллбэком на `product_costs` по артикулу/баркоду, если для
конкретной поставки совпадения нет. Плюс добавляю проверку: если проданный товар не нашёлся
ни в таблице поставок, ни в фоллбэке — в интерфейсе ОПиУ появится уведомление с конкретными
`gi_id`/баркодами, чтобы я не теряла данные и оперативно вносила себестоимость новых поставок.
Всё это просто не заработает по назначению, пока `gi_id` не появится в базе.
