# Сквозной аудит продукта — finance-panel

Дата: 12–13 сентября 2026. Ветка `feat/rk-dense-default` (коммит `d754487c`), только чтение — код не менялся, приложение проверялось локально с реальными внешними интеграциями (WB/Ozon), но все опасные вызовы были заблокированы на уровне сети (см. §F).

Состав работы: разбор кода 73 экранов и 267 API-роутов силами параллельных агентов → браузерный обход всех экранов на 4 профилях экрана (Playwright, реальный dev-сервер) → состязательная проверка 156 находок независимыми агентами по 40 файлам-корням (18 отклонено как ложные срабатывания) → семь тематических разборов (роли, интеграции, дизайн, расчёты, сценарии, навигация, тесты).

Полные данные: `data/verified-findings-full.json` (156 разобранных находок с вердиктом), `data/topic-*.md` (семь тематических отчётов), `data/crawl-desktop.json` + `evidence/*.png` (129 скриншотов), `data/summary.json` (техпроверки).

## A. Резюме

**Продукт работоспособен и в целом качественно сделан.** Обход всех 71 достижимого экрана на десктопе, телефоне (390px) и iPad (портрет и альбом) не нашёл ни одного краша, ни одного горизонтального скролла, ни одной страницы с ошибкой сервера. Ядро ценности — воронка WB, юнит-экономика, ОПиУ, журнал рекламы, склад — работает и местами очень зрело спроектировано: явная дисциплина «честного нуля» (отсутствие данных не превращается в 0), инварианты ДДС с собственными тестами, продуманная деградация при недоступности внешних API.

**Но у продукта есть подтверждённая, серьёзная дыра в границе между организациями.** Внешний контур (клиенты-селлеры со своими организациями) защищён кодом, который писался для роли `seller`, но забыл про `seller_owner` — более позднюю, более широкую внешнюю роль. Это не единичный баг, а один системный дефект, повторённый минимум в шести независимых местах кода (proxy.ts, `cabinetAccess.ts`, `app/api/cabinets/route.ts`, `getActiveOzonCreds`, `/api/reviews`, `/api/opiu/margin`), из-за чего в закономерном состоянии «клиента только что завели, кабинет ещё не назначен» этот пользователь получает данные ЧУЖИХ организаций: чужие кабинеты WB и Ozon, чужую прибыль и себестоимость, чужие отзывы. Каждое из этих мест перепроверено я лично прямым чтением кода, не только агентом.

**Второй системный класс проблем — опечатка, полностью останавливающая модуль.** Оператор запятой вместо `&&` в одной строке (`lib/adverts/cabinetGuard.ts:75`) делает условие проверки роли всегда истинным, из-за чего **весь модуль управления рекламой** (запуск/пауза кампаний, ставки, депозиты, автоправила — 9+ роутов) отвечает 403 директору. Направление безопасное (отказ, а не дыра), но это полный отказ работоспособности ключевого коммерческого инструмента, и обход состязательной проверки нашёл ту же строку четыре раза с разных сторон — она не заметна при обычном код-ревью, потому что похожа на рабочий код.

**Третий класс — расхождение документации и продукта.** `README.md` описывает три роли вместо десяти и называет актуальными экраны (`/rnp`, `/seo`, `/sklejki`), которые давно осиротели и не выводятся в меню. `docs/wb-ops-runbook.md` описывает kill-switch (`ADVERT_DOCKING_OFF`) для остановки автоматики, которого в коде давно нет — если владельцу срочно понадобится экстренно остановить трату бюджета на рекламу, инструкция в его собственном runbook ничего не остановит.

**Рекомендуемая последовательность действий:**
1. Немедленно — три строки кода, дающие межарендную утечку (см. P0-01) и одна строка с опечаткой (P0-02). Обе правки маленькие, локализованные, с готовой формулировкой в §C.
2. В течение недели — 5 P0-находок про склад/дизайн/КИЗ/удаление кабинета/costs (§C), плюс синхронизация `README.md` с реальностью (дёшево, заметно для новых участников).
3. Системно — тестовый гейт не защищает продукт от регрессий (треть тестов проверяет текст файла, а не поведение; PR-гейт вообще не запускает `npm test`); это объясняет, почему опечатка в `cabinetGuard.ts` и утечка `seller_owner` дожили до прода незамеченными.

## C. Реестр проблем

Приоритеты: **P0** — подтверждённая критическая проблема (потеря данных, несанкционированный доступ, полная неработоспособность ключевой функции без обхода). **P1** — серьёзно нарушен основной сценарий. **P2** — локальная ошибка с обходным путём. **P3** — косметика.

Полные детали каждой находки (evidence, failureScenario, sourceFile) — в `data/verified-findings-full.json`, где к каждому заголовку ниже можно найти запись по точному тексту `title`.

### P0 — сделать немедленно

**P0-01. Внешний главный пользователь клиента (`seller_owner`) видит данные чужих организаций — один системный дефект в шести местах.**
- Раздел: платформа/безопасность. Роль: `seller_owner` (и любой мультиролевой внешний пользователь) в состоянии пустого `cabinet_ids` — штатное состояние сразу после регистрации, до назначения кабинетов.
- Категория: безопасность. Затронутые места (все — независимо подтверждены и мной лично для трёх из них):
  1. `app/api/cabinets/route.ts:63` — фильтр по организации применён только к `session.role === "seller"`; `seller_owner` получает `allCabinets` (WB+Ozon) без фильтра.
  2. `lib/auth/cabinetAccess.ts:15-24` (`sessionHasCabinetAccess`) — есть явная ветка «пустой cabinet_ids = нет кабинетов» только для `seller`; `seller_owner` проваливается в общую ветку, где пустой список = «все кабинеты».
  3. `lib/ozon/cabinet.ts:103,205` (`getActiveOzonCreds`/`getOzonCabinetScope`) — тот же паттерн для Ozon-кабинетов.
  4. `app/api/opiu/margin/route.ts` через `apiPermissions.ts:79` — эндпоинт закрыт `analytics.view`, которым обладает `seller_owner`; узкий deny-by-default список в `proxy.ts:221` (`roles.length===1 && roles[0]==="seller"`) на `seller_owner` не срабатывает → внешний клиент получает прибыль и себестоимость по артикулам владельца.
  5. `app/api/reviews/route.ts` — в режиме `?cabinet=all` (дефолт экрана `/wb/reviews`) отзывы отдаются без границы организации тем же путём.
  6. `app/api/agent/insights` — лента инсайтов не привязана к кабинету/организации вовсе, доступна любой роли с `analytics.view`, включая внешнюю.
- Шаги воспроизведения: завести пользователя с ролью «Внешний менеджер (главный)» без назначения кабинета (штатный порядок по `docs/EXTERNAL_WB_SELLERS.md:22-23`) → залогиниться → `GET /api/cabinets` без параметров.
- Ожидаемо: список кабинетов своей организации (или пусто). Фактически: активные кабинеты WB и Ozon всех организаций в системе.
- Влияние: прямое нарушение договорного обещания изоляции данных клиентов, прописанного в `docs/EXTERNAL_WB_SELLERS.md:34` («убедиться, что каждый видит только свой кабинет»); риск для всех будущих внешних клиентов панели.
- Причина (подтверждена): все шесть мест писали проверку как `role === "seller"` буквально, вместо использования уже существующей функции `isExternalRole`/`rolesAreExternal` (`lib/auth/permissions.ts:132-134,367-369`); роль `seller_owner` введена позже `seller` и не была дописана ни в одно из шести мест.
- Рекомендация: один хелпер `isExternalSession(session) = rolesAreExternal(sessionRoles(session))`, заменить им все шесть точечных сравнений с `"seller"`. Плюс тест по образцу `multi-role.test.mts` (сканирование кодовой базы на копии сравнения с ролью-строкой рядом с логикой границы кабинета/организации).
- Критерии приёмки: вымышленная сессия `seller_owner`/`cabinet_ids=[]` получает 403 или пустой список на всех шести путях; существующие тесты `external-contour.test.mts` расширены проверкой именно для `seller_owner`, не только `seller`.
- Сложность: S (сам хелпер и замена — часы), но с высокой неопределённостью объёма — нужен полный аудит всех использований `role === "seller"` по кодовой базе, а не только найденных шести (см. рекомендацию теста).

**P0-02. Оператор запятая вместо `&&` останавливает весь модуль управления рекламой для всех ролей.**
- Раздел: `/wb/adverts` и 9+ API (`action`, `bid`, `create`, `bulk`, `deposit`, `minus`, `rules`, `rename`, `journal`, `config`, `clusters`, `token`). Роль: все, включая `director`.
- Категория: функциональность (P0 по критерию «полная неработоспособность ключевой функции без обхода»).
- Шаги: залогиниться `director` → `/wb/adverts` → пауза любой кампании.
- Ожидаемо: кампания приостановлена. Фактически: 403 «Недостаточно прав для управления рекламой» — для любой роли.
- Код: `lib/adverts/cabinetGuard.ts:75` — `if (session.role !== "director" && session.role !== "wb_manager", "ozon_manager")`. Приоритет операторов делает всё выражение равным строке `"ozon_manager"` (truthy) → `if` всегда истинен.
- Влияние: полный отказ коммерчески ключевого модуля; подтверждено `git blame` как регрессия конкретного коммита `9be1808f` (#959, 09.09.2026) при переносе на новую ролевую модель.
- Рекомендация: `const roles = sessionRoles(session); if (!roles.some(r => r === "director" || r === "wb_manager" || r === "ozon_manager")) return 403;` — заодно чинит смежный P1 (многоролевость игнорируется в этом же месте).
- Критерии приёмки: `director`/`wb_manager`/`ozon_manager` с одной ролью и с несколькими ролями проходят гейт; прочие роли получают 403.
- Сложность: S. Одна строка, но требует ручной проверки на живом кабинете после исправления (тест на текст условия легко написать регэкспом — как раз тот случай, где это уместно, поскольку речь о синтаксисе, а не о поведении).

**P0-03. Экран «Эффект правок карточек» (`/api/design`) — утечка данных и IDOR по всем трём методам.**
- Раздел: PIM/карточки. Роли: любая с `catalog.edit`/`analytics.view`, прошедшая узкие списки прокси (`director`, `wb_manager`, `seller_owner` при одиночной роли).
- Категория: безопасность.
- GET: нет фильтра по кабинету — видны `card_changes` и воронка любого кабинета/организации.
- POST: право проверено картой (`catalog.edit`), но владение кабинетом, к которому относится `nm_id`, не проверяется вовсе — можно записать «правку карточки» на чужой кабинет.
- DELETE: удаление записи по произвольному `id` без проверки владения (классический IDOR).
- Рекомендация: перед каждой операцией вызывать `hasCabinetAccess` для кабинета, к которому фактически относится `nm_id`/запись (аналогично уже работающему `app/api/design/day-metrics/route.ts`).
- Критерии приёмки: запрос с `nm_id`/`id` чужого кабинета отвечает 403 на всех трёх методах.
- Сложность: S–M (нужно резолвить `nm_id → cabinet_id` через `wb_cards`, паттерн уже есть в соседнем роуте).

**P0-04. `GET /api/warehouse/kiz` без параметра `entity` отдаёт агрегат по ВСЕМ юрлицам любой сессии с `warehouse.view`.**
- Категория: безопасность. Затрагивает cabinet-scoped `wb_manager`/`ozon_manager` с ограниченным `cabinet_ids`, а также внешних `seller_owner`.
- Рекомендация: при отсутствующем `entity` брать `listAccessibleEntities()` сессии, а не `null`, и агрегировать только по доступным юрлицам.
- Сложность: S.

**P0-05. Роль `hr` жёстко исключена из проверки `/api/finance/payroll` и `/api/payroll`, хотя по карте прав ей назначены `payroll.view`/`payroll.edit` — единственный модуль этой роли не работает вовсе.**
- Категория: функциональность. Затрагивает: весь штат HR.
- Код: `requireApiSession([...])` в роуте не включает `"hr"` — расхождение с матрицей прав. Единственная роль, у которой это единственный назначенный модуль, полностью недоступна.
- Рекомендация: добавить `"hr"` в список авторизованных ролей роута.
- Сложность: S — но стоит проверить вживую с реальной ролью `hr`, это не только код.

**P0-06. Каталог себестоимости (`/api/costs`) собирается по всем кабинетам на GET и пишется без границы юрлица на POST.**
- Категория: безопасность/данные. GET: каталог WB минует область сотрудника (cabinet-scoped роль видит себестоимость чужих кабинетов). POST: `product_costs` не имеет tenant-ключа — запись по артикулу глобальна, то есть внешний клиент технически может перезаписать себестоимость товара с тем же артикулом у владельца или другого клиента (если артикулы совпадут).
- Рекомендация: GET — фильтровать кабинеты через `hasCabinetAccess` перед сборкой каталога (паттерн уже есть в `wb/sync-health`); POST — добавить составной ключ (organization_id, article) в `product_costs`.
- Сложность: M (изменение схемы для POST-части).

**P0-07. Необратимое каскадное удаление кабинета (`DELETE /api/cabinets/[id]`) без журнала и без проверки существования.**
- Категория: безопасность/данные. Роль: `director`. Срабатывает штатной кнопкой «Удалить», без нужды в эксплойте.
- Рекомендация: перед удалением читать кабинет (404 при отсутствии), писать в `access_audit_log` полное состояние до удаления.
- Сложность: S.

**P0-08. `DELETE /api/content/upload` проверяет принадлежность файла подстрокой URL, а не сегментом пути — плюс удаление из хранилища не зависит от того, была ли запись в каталоге.**
- Категория: безопасность (IDOR-подобный класс). Рекомендация: разбирать `target` как настоящий URL, сравнивать `pathname` на точной позиции; выполнять `storage.remove()` только после подтверждённого владения.

## E. Что сохранить

- **Дисциплина «честного нуля/null» в расчётах.** Подавляющее большинство денежных метрик явно возвращает `null`, когда посчитать нечем, вместо вводящего в заблуждение нуля — задокументировано прямо в коде с описанием реальных прод-инцидентов, которые эта дисциплина предотвращает. Есть отдельный тест-файл именно на эту дисциплину (`lib/finance/pnlHonesty.test.mts`).
- **Инварианты ДДС** (`docs/DDS-RULES.md`) держатся собственными тест-сторожами, а не только описанием — редкая для проекта такого размера зрелость.
- **Механизмы здоровья интеграций** (`sync-log`, `watchdog`, `token-health`, `operational-health`, `wb/sync-health`) — многослойная, продуманная система обнаружения деградации внешних API, включая специальную проверку «крон отчитался ok, но данные реально не обновились» (`syncFactVerdict`), возникшую из реального прод-инцидента.
- **Мобильная адаптация.** Обход всех 71 экрана на четырёх профилях не нашёл ни одного случая горизонтального прокручивания — редкий результат для продукта с таким количеством широких таблиц; система классов `.tap`/`.tap-hit`/`.scroll-x` реально работает почти везде.
- **Честная диагностика внешних барьеров.** Там, где действие физически невозможно (read-only WB-токен для рекламы, отсутствие записи в FBW API для упаковки поставки), панель не притворяется, что действие сработало — переводит отказ WB в понятную фразу и даёт заранее проверить возможность действия.
- **История самоисправлений в кронах.** Логи и комментарии показывают минимум пять конкретных прод-инцидентов синхронизации, которые были найдены и исправлены с сохранением объяснения в коде (пропущенные дни продаж, зависший бэкфилл Ozon-рекламы, крон, который планировщик не мог вызвать методом GET) — команда умеет находить и чинить такие проблемы, что видно по качеству комментариев.

## F. Ограничения

**Роли, кроме `director`, проверены только чтением кода.** У меня не было (и я не запрашивал) реальных тестовых учётных записей для 9 остальных ролей — создание новых пользователей в боевой базе является действием с последствиями, выходящим за рамки read-only аудита без отдельного разрешения владельца. Поэтому утверждения о доступе `seller_owner`, `hr`, `buyer` и других некий этих ролей основаны на анализе `proxy.ts`/`apiPermissions.ts`/`cabinetAccess.ts`, а не на живом входе под этой ролью. Риск: возможны нюансы поведения, которые проявляются только при реальной сессии (например, порядок редиректов, специфичные для конкретных данных в базе). **Что нужно для завершения**: тестовые учётные записи по одной на роль (без реальных прав на прод-данные) или явное разрешение временно создать их.

**Формулы расчётов не пересчитаны на живых числах.** Пять формул маржи и четыре формулы GMROI прочитаны и сопоставлены между собой (расхождения задокументированы в §C/теме «Расчёты»), но ни один расчёт не был вручную пересчитан по реальным данным и сверен с тем, что показывает экран. Контрольные проверки (какой GET дёрнуть, как пересчитать вручную) предложены в теме «Расчёты и метрики», но не выполнены. **Что нужно**: доступ к реальным данным кабинета и время на ручной пересчёт 5 метрик.

**Ozon-модуль проверен мельче, чем WB-модуль.** Гейты доступа разобраны, но полная логика расчётов Ozon-кокпита (`lib/ozon/cockpit.ts`, `/ozon/economy`, `/ozon/unit`) не прочитана построчно — по памяти проекта на конец августа там уже была отдельная волна из 111 находок с планом в 4 фазы, и глубина этого прохода недостаточна, чтобы утверждать, что там нет новых проблем того же масштаба, что найдены для WB. **Риск**: непроверенная часть могла остаться неизменной с августовского аудита или частично исправленной — нужен отдельный проход.

**Не проверены построчно** (из-за объёма): `lib/opiu/monthlyStatement.ts` (месячный ОПиУ на `/pnl`) — только структура; `lib/rnp/operatingMatrix.ts` (1022 строки) — подтверждено использование поля `gmroi`, не проверено, не пятая ли это реализация с ещё одним клампом; `lib/unit/priceSolver.ts` — шестая по счёту формула маржи (обратная задача подбора цены), не сопоставлена с остальными пятью; складской модуль (`lib/warehouse/*`, 26 файлов) не разбирался в рамках темы «расчёты», хотя частично затронут в реестре проблем через отдельные находки.

**Обход браузером использует dev-сервер (`next dev`), не прод-сборку.** Время отклика, зафиксированное в `crawl-desktop.json`, отражает компиляцию модулей при первом заходе (некоторые значения — 50-90 секунд), а не реальную скорость в проде на Vercel. Для честного замера производительности нужен отдельный проход на `next build && next start` или на самом проде.

**Метод безопасности обхода**: локальное окружение подключено к реальной продовой базе Supabase и реальным API-ключам WB/Ozon. Чтобы браузерный обход не мог случайно записать данные или потратить деньги/лимиты, вся сетевая обвязка на уровне Playwright обрывала: все не-GET запросы к приложению; GET-запросы к 89 эндпоинтам, классифицированным как небезопасные (живые внешние вызовы, синки, платные сервисы); любые не-GET запросы к внешним хостам. Список небезопасных путей выведен из состязательной проверки API (не только из беглой классификации) — в процессе работы нашлась и исправлена ошибка первой версии списка (RNP-таблица ошибочно помечена как «ходит в WB», хотя читает только кэш). Самопроверка обвязки перед началом обхода подтвердила: POST/DELETE к живым эндпоинтам обрываются на уровне сети, GET к безопасным эндпоинтам доходит до сервера.
