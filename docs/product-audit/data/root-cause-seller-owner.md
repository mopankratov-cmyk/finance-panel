# Системный корень: seller_owner не признан внешней ролью в трёх местах

Все проверенные P0-находки (кроме бага-запятой в рекламе) сводятся к ОДНОЙ причине,
повторённой в трёх независимых местах кода. Автор явно закрывал дыру для роли
`seller` (внешний сотрудник), но каждый раз забывал `seller_owner` (внешний
ГЛАВНЫЙ пользователь клиента) — хотя обе роли относятся к одному внешнему контуру
(isExternalRole в lib/auth/permissions.ts:132 включает обе).

## Три места одной дыры

1. **proxy.ts:118-131** — deny-by-default списки (isSellerApiAllowed и т.д.)
   применяются только при `roles.length === 1 && roles[0] === "seller"`.
   Для `seller_owner` условие никогда не срабатывает → запрос идёт дальше,
   к общей карте прав apiPermissionFor, которая для многих путей (analytics.view,
   /api/opiu/margin и др.) слишком широка для внешнего контура.

2. **lib/auth/cabinetAccess.ts:15-24** (sessionHasCabinetAccess) — есть отдельная
   ветка `if (session.role === "seller")`, которая ЯВНО запрещает пустой
   cabinet_ids трактовать как «все кабинеты» (комментарий: «они не должны
   пересечь tenant-границу»). Для seller_owner эта ветка не входит, и код
   проваливается в общую (для внутренних ролей) ветку строки 24, где пустой
   cabinet_ids = «все кабинеты» — ИМЕННО ТО, что было запрещено строкой выше
   для соседней внешней роли.

3. **app/api/cabinets/route.ts:63** — org+cabinet_ids фильтр применяется
   только при `session.role === "seller"`; seller_owner получает
   `allCabinets` без фильтра по организации.

## Почему это один дефект, а не три

Правило, которое должно быть написано один раз и переиспользовано:
  "любая внешняя роль (isExternalRole), а не только role==='seller' и не
  только одиночная роль (roles.length===1), обязана: (а) проходить deny-by-default
  список путей своего контура, (б) трактовать пустой cabinet_ids как 'нет
  кабинетов', а не 'все кабинеты', (в) быть отфильтрована по organization_id
  везде, где идёт агрегация по кабинетам компании."

Вместо этого правило написано ad hoc по имени роли в трёх разных файлах,
и во всех трёх новую роль seller_owner (введена позже, чем seller) забыли
дописать. Это тот же класс бага, что и «пять копий словаря ролей» из
memory/panel-access-model.md — только на уровне границы арендатора, а не
названия роли.

## Практическая проверка (можно повторить в режиме чтения)

Вымышленная сессия role=seller_owner, cabinet_ids=[] (ровно то, что получает
свежезаведённый главный пользователь клиента ДО того, как ему назначили
кабинеты — обычный порядок работы: сначала завели учётку, потом кабинеты):
- GET /api/cabinets → все активные кабинеты WB+Ozon всех организаций (не только своей)
- GET /api/opiu/margin?brand=norvia → прибыль и себестоимость владельца
- GET /api/reviews (без ?cabinet=) → отзывы по всем организациям
- sessionHasCabinetAccess(session, "чужой-кабинет-id") → true

## Рекомендуемая починка (одна, не семь)

Один хелпер `isExternalSession(session)` = `rolesAreExternal(sessionRoles(session))`
(функция rolesAreExternal уже существует, permissions.ts:368), и заменить во
всех трёх местах:
- `session.role === "seller"` → `isExternalSession(session)`
- `roles.length === 1 && roles[0] === "seller"` → `roles.every(isExternalRole)`
  (мультиролевой внешний+внутренний уже запрещён при создании пользователя —
  api/users/route.ts проверяет это — так что `every` эквивалентно `some` на
  практике, но `every` безопаснее при будущих изменениях)

Плюс тест по образцу multi-role.test.mts (сканирование кода на копии словаря
ролей), но для паттерна `role === "seller"` — искать по всей кодовой базе
одиночные сравнения с ролью там, где рядом есть isExternalRole/rolesAreExternal,
и требовать использовать общую функцию.
