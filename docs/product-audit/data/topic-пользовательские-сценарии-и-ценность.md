## 0. Главный вывод, до деталей

Продукт живёт на **двух архитектурах одновременно**, и верхнеуровневые документы (`README.md`, `STRUCTURE.md`) описывают только старую:

- **Роли.** `README.md:29` и `STRUCTURE.md:120-128` утверждают: RBAC из трёх ролей — `director / finance / manager`. Реальный код (`lib/auth/permissions.ts:102-114`) — это **10 ролей** с отдельной матрицей действий (`ROLE_PERMISSIONS`, `lib/auth/permissions.ts:190-287`): `director, fin_director, financier, hr, wb_manager, ozon_manager, buyer, warehouse, seller_owner, seller`. Внешний многотенантный контур (клиент-селлер со своей организацией) в верхних доках не упомянут вовсе.
- **Навигация.** `README.md:11-17` называет разделы `/rnp`, `/seo`, `/sklejki` текущими экранами продукта. В коде это — работающие, но осиротевшие дубликаты старого поколения (см. §3.5); настоящие рабочие экраны — `/wb/rnp`, `/wb/seo`, `/wb/sklejki`, на которые и ведёт `components/Sidebar.tsx:71-83`.

Это не косметика: onboarding-документ прямо отправляет нового участника (человека или его Claude Code) читать `README.md` первым (`docs/ONBOARDING.md` не переопределяет разделы), и он получает карту продукта, которая не совпадает с тем, что видит директор в интерфейсе.

## 2. 18 сквозных сценариев

Формат: **Роль → цепочка экранов/API → ожидаемый результат на каждом шаге**. Статус в конце: ✅ работает по замыслу, ⚠️ работает с оговоркой/внешним ограничением, 🔴 обрывается незавершённостью.

**1. Утренний контроль воронки → решение о цене (wb_manager / seller).**

**2. Управление жизненным циклом рекламной кампании (wb_manager / seller).**

Перед этим панель уже сама умеет спросить у WB, умеет ли ключ писать (`probeWriteAbility`, `lib/wb/advertApi.ts:282`), и показывает вердикт в `components/wb/ads/AdTokenPanel.tsx:43`. Статус: ⚠️ — механизм диагностики зрелый (не «мёртвая кнопка», а честный отказ с причиной), но реальное действие зависит от внешнего факта — выдан ли на кабинете WB-ключ с правом записи (`docs/отложено.md:32-33`, «⚠️ Управление рекламой требует WRITE-токена»).

Статус: ✅, но зависит от того же write-токена, что и сценарий 2.

### C. Финансы и ДДС

**12. Платёжный календарь: план → факт (financier / fin_director).**
`/calendar` → факт закрывает план только при точном совпадении суммы (±1%), иначе — ручное подтверждение (инвариант I2, `docs/DDS-RULES.md:36`) → факт, уже помеченный `[calendar-fact:]`, не предлагается повторно ни календарю, ни сверке кредитов, ни зарплате (инвариант I1, `consumedFactIds()`, `lib/finance/factLinks.ts`). Статус: ✅, инварианты держатся тест-сторожами (`lib/finance/planFactExclusive.test.mts`).

**13. Импорт банковской выписки → классификация (financier).**
`/payments` → «Импорт ДДС» (`components/payments/ImportDdsModal.tsx`) → XLSX разбирается детерминированно, PDF — ИИ (`lib/finance/bankStatementServer.ts`) → при неоднозначности (пустой владелец выписки, два подходящих кошелька, одна похожая операция) система честно отвечает «не знаю» + `needsReview`, а не берёт первый попавшийся вариант (инвариант I7, `lib/opiu/bankOwnerGuess.test.mts`). Статус: ✅ по духу; **живая проверка на реальной выписке > 4 МБ отмечена как не пройденная** (`docs/DDS-RULES.md:143`, п.1 открытого списка).

**14. Кредиты: договор → график → сверка (financier).**
`/loans` → распознавание договора ИИ (`lib/loans/recognizeLoan.ts`) → график как отдельная сущность `loan_schedule_rows` (`lib/loans/scheduleModel.ts`) → закрытие строки фактом ДДС помечает `[paid-by:<factId>]`. Статус: ✅ для новых договоров; **старые договоры, заведённые до миграции `loan_schedule_rows`, ещё читаются по текстовым меткам в `comment` и переезжают на строки только при первом пересохранении** (`docs/DDS-RULES.md:147`) — переходный период, не поломка, но источник расхождений, если пересохранения не было.

**15. Зарплатная ведомость (hr / director для реквизитов).**
`/payroll` → вкладка «Штат» → импорт Excel (`«Обновить данные из Excel»`) → вкладка «Реквизиты» — банковские данные видит только `director` (`canViewPrivate`, серверный флаг `data.canViewPrivate`, проверено на `components/payments/PayrollRegister.tsx:469`) → «Ведомость» расчёт → `payroll.approve` только у `fin_director`/`director`. Статус: 🔴 частично — код-гейт на месте, но `docs/DDS-RULES.md:143-144` прямо перечисляет это как **не пройденную живую проверку**: первая реальная ведомость 5-го/20-го, распределение одной реальной выплаты, и отдельно — «вход под `finance`(financier) на «Реквизиты» должен давать отказ» ещё не проверен на живых данных, хотя сама роль `financier` в матрице прав вообще не имеет `hr.view`/`payroll.view` (`lib/auth/permissions.ts:222-229`), то есть по коду не должна даже попасть на экран.

**16. Финрезультат: три параллельных источника правды (fin_director, director).**
`/pnl` (месячный управленческий P&L), `/opiu` («Финансовый отчёт WB», понедельная детализация), `/pnl/balance` (баланс) — заявлены как разные назначения (`docs/OPIU-PLAN.md:17-23`), но **методологически всё ещё расходятся** (база для процентов, себестоимость возвратов) — открытый пункт §6.4 `docs/DDS-RULES.md:146`. Статус: 🔴 — пользователь, сверяющий «чистую прибыль» между `/pnl` и `/opiu` за один период, законно получит разные числа, и это задокументированный, не случайный факт.

**17. «Где теряем» / «Сводка» (fin_director, director).**
`/losses`, `/summary` — удержания по статьям. Ноль трактуется как «не посчитано», а не как факт (инвариант I4, `lib/finance/pnlHonesty.test.mts`, упомянут в `docs/DDS-RULES.md:38`). Статус: ✅.

### D. Операции: закупки и склад

**18. Закупки → приёмка → раскладка по коробам → поставка WB (buyer).**
`/supplies` (или `/wb/supplies` для менеджера) → расчёт потребности → заказ → загрузка «готовой тары» `containerscontent.xlsx` → раскладка целыми коробами по сохранённым долям → dry-run → отдельный номер поставки WB на склад → **упаковку в кабинет WB загружают вручную**, потому что официальный FBW API отдаёт только чтение `/package`, без записи (`docs/отложено.md:19`, «Остаётся вне автоматизации»); панель после ручной загрузки перепроверяет состав через FBW API и не показывает фиктивное «загружено». Статус: ⚠️ — задокументированный, а не случайный внешний барьер.

**22. Онбординг внешнего селлера — изоляция между организациями (seller_owner). ПРОВЕРЕННАЯ НАХОДКА.**
Порядок по документу: директор заводит пользователя с ролью «Внешний селлер» **без назначения кабинета** (`docs/EXTERNAL_WB_SELLERS.md:22-23`, «Кабинет вручную ему не назначается»), затем человек сам подключает кабинет через сценарий 21. Между этими двумя шагами у `seller_owner` `cabinet_ids = []`. В этот момент:
- `proxy.ts:221` пропускает deny-by-default список только при `roles.length === 1 && roles[0] === "seller"` — для `seller_owner` условие никогда не срабатывает, и запрос уходит в общую карту прав, которая для `seller_owner` шире, чем нужно внешнему контуру.
- `lib/auth/cabinetAccess.ts:15-24` (`sessionHasCabinetAccess`) содержит отдельную ветку `if (session.role === "seller")`, которая явно трактует пустой `cabinet_ids` как «нет кабинетов». Для `seller_owner` эта ветка не срабатывает, код проваливается в строку 24 (`if (!isCabinetScopedRole(session.role) || session.cabinet_ids.length === 0) return true;`) — а `isCabinetScopedRole("seller_owner")` истинно (`lib/auth/permissions.ts:143-145`), поэтому условие даёт `false || true = true`: доступ к **любому** `cabinetId` разрешён.
- `app/api/cabinets/route.ts:63-68` — фильтр по организации применяется только при `session.role === "seller"`; `seller_owner` в состоянии `cabinet_ids=[]` получает `allCabinets` без фильтра — активные кабинеты WB и Ozon **всех** организаций, не только своей.

Это прямо нарушает пункт приёмки `docs/EXTERNAL_WB_SELLERS.md:34` («убедиться, что каждый видит только свой кабинет»). Причина одна и та же в трёх местах — код разделял `seller` и `seller_owner` там, где обе роли относятся к `isExternalRole` (`lib/auth/permissions.ts:132-134`), и `seller_owner` как более позднюю роль забыли дописать во все три проверки.

## 3. Где сценарии обрываются незавершённостью — сводка по типам

### 3.1 Управление рекламой заперто внешним фактом, но диагностируется честно
`docs/отложено.md:32-33` называет это прямо: `WB_TOKEN_ADVERT` — read-only. Код (`app/api/adverts/action/route.ts:12-26`, `lib/wb/advertApi.ts:260-282`) не притворяется, что действие сработало: переводит `403 read-only token…` в понятную фразу и даёт заранее проверить право записи (`probeWriteAbility`, `app/api/adverts/token/route.ts:58`). Это не «мёртвая кнопка» в смысле бага — это честно объяснённый внешний барьер.

### 3.2 CTR-тест: автоматика однажды выглядела включённой, не будучи такой
`app/api/ctrtest/rotate/route.ts:66-77` — прямое признание в коде: планировщик Vercel вызывает крон методом `GET`, а роут был объявлен только `POST`, поэтому 29 часов подряд ротация не срабатывала ни разу (30 352 показа при норме раунда 350), при этом на экране «автоматика выглядела включённой» — ни ошибка, ни `auto_checked_at` не проставлялись. Сейчас `GET`/`POST` экспортируются оба (строки 79-85) — конкретный инцидент исправлен, но иллюстрирует класс риска: у автоматических экранов нет общего механизма «включено и работает» vs «включено и молчит», кроме индивидуального `auto_error` поля.

### 3.3 Устаревший runbook описывает несуществующий контур управления
`docs/wb-ops-runbook.md:11, 27, 37, 49-51` описывает маршрут `/ad-docking`, API `/api/adverts/dock*`, крон `/api/adverts/dock/cron` и env-выключатели `ADVERT_DOCKING_OFF`, `CTRTEST_OFF`, `CTRTEST_PHOTO_SWAP_LIVE`. Проверка показывает:
- `app/api/adverts/dock*` и страницы `/ad-docking` в дереве `app/` не существует вовсе (см. полный список `app/api/adverts/*` в разделе исследования — только `journal, token, bulk, deposit, cpm-reco, minus, config, changes, clusters, deposits, action, list, rules, bid, rename, create`).
- Ни `ADVERT_DOCKING_OFF`, ни `CTRTEST_OFF`, ни `CTRTEST_PHOTO_SWAP_LIVE` не встречаются нигде в `app/` и `lib/` (полнотекстовый поиск — ноль совпадений).
- Реальные крон-пути в `vercel.json` — `/api/adverts/rules/run` и `/api/ctrtest/rotate`, с управлением через БД-флаги на уровне отдельного правила/теста (`components/wb/ads/AdRulesTab.tsx`, `app/api/ctrtest/[id]/action/route.ts:93`), а не через переменные окружения.

Практическое следствие: если человек, ответственный за деньги, захочет **экстренно остановить** автоматическое докидывание бюджета так, как написано в его собственном runbook (`ADVERT_DOCKING_OFF=1`), это действие ничего не остановит — описанного кода давно нет. Это самый серьёзный разрыв «документация ⇄ код» из найденных, потому что он про финансовый kill-switch.

### 3.4 Проверенная брешь multi-tenant изоляции для `seller_owner`
Разобрана целиком в сценарии №22 выше, с тремя точными местами кода: `proxy.ts:221`, `lib/auth/cabinetAccess.ts:15-24`, `app/api/cabinets/route.ts:63-68`. Единственная первопричина — проверки писались как `role === "seller"` вместо `isExternalRole(role)`/`rolesAreExternal(roles)` (готовая функция уже существует, `lib/auth/permissions.ts:367-369`), и `seller_owner`, добавленный позже как более широкая внешняя роль, в три места не попал.
