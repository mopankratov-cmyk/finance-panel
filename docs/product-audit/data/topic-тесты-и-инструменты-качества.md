Ключевые факты о `test`:
- Раннер — встроенный `node:test`, файлы транспилируются `tsx` (esbuild-подобный транспайлер: **стирает типы, не проверяет их**). Type-check в `npm test` не входит.

- `build` — `next build --webpack`; отдельно `--webpack` уже сам по себе намёк на нестандартность сборки (Next 16 по умолчанию тянет к Turbopack — см. предупреждение в `AGENTS.md:1-3` про несовпадение с обучающими данными).

## 3. Поведение vs. regex-по-исходнику

Это ключевой структурный факт репозитория.

**Метод проверки**: для каждого теста проверялось, вызывает ли он реальный код (`import { fn } from "../lib/..."`, дальше `fn(...)`+`assert`) или читает файл как текст (`readFileSync`/`readFile(new URL(...))`) и матчит его регулярками (`assert.match` / `assert.doesNotMatch` / `.includes()` / `indexOf()`-сравнения позиций).

Цифры:
- **121 файл из 357 (34%)** используют `readFileSync`/`readFile` внутри теста.
- **198 отдельных вызовов** чтения именно `.ts`/`.tsx`-исходников (не фикстур) внутри тестов.
- **92 файла из 357 (26%)** не импортируют вообще ни одной функции из `lib`/`app`/`components` — весь файл целиком состоит из regex-проверок над текстом чужого исходника. Список — `/tmp/pure_regex_files.txt` (сформирован при аудите), примеры ниже.
- Из 267 route-файлов (`app/api/**/route.ts`) только 114 хоть раз упоминаются в тестах — и почти всегда именно как **строка для чтения**, а не как импортируемый обработчик, вызванный с моком запроса.
- Ни один компонент нигде не рендерится: в `package.json` нет `@testing-library/react`, `jsdom`, `happy-dom`, `jest`, `vitest` — их просто нет в зависимостях. Каталоги `components/wb` (59 файлов), `components/warehouse` (23), `components/ozon` (15), `components/ui` (12) не имеют ни одного `*.test.mts` рядом — вся их «проверка» (там, где она вообще есть) идёт через `tests/*.test.mts`, читающие эти `.tsx` как строку.

Примеры regex-по-исходнику (не поведение):

- `tests/full-data-audit-regression.test.mts:9-21` — первый тест файла читает 4 route/lib-файла и делает 8 `assert.match`/`assert.doesNotMatch` по именам функций и строкам SQL (`from("wb_report_rows")`, `getOzonCabinetScope` и т.п.). Ни одна функция не вызывается — это грамматика исходников, не поведение системы.
- `tests/unit-group-ui.test.mts:1-70` — весь файл (7 тестов) целиком состоит из чтения `app/unit/page.tsx`, `components/opiu/MarginByArticlePage.tsx`, `components/opiu/UnitMarginPage.tsx`, `components/CabinetSwitcher.tsx` и т.д. и текстовых assert'ов по строкам вроде `/<FinanceTabs\s*\/>/` или сравнения `indexOf("{loading ?")` с `indexOf("data && data.rows.length")`. Ни одного `import` рабочей функции нет — файл проверяет, что в коде **написаны нужные слова в нужном порядке**, а не что компонент так себя ведёт.
- `tests/unit-margin-safety.regression.test.mts:1-134` — смешанный: тесты в строках 8-73 реальные (импортируют и вызывают `parseUnitCabinetScope`, `isConfiguredCronBearer`, `parseUnitMoneyQuery` и т.д.), а с теста `"unit table dual auth..."` (строка ~76) до конца файла (строка 134) — снова текстовый разбор `app/api/unit/table/route.ts` через `indexOf`/`assert.match` по сигнатурам и порядку строк в файле.
- `lib/ai/models.test.mts:1-16` — примечательно, что это файл **внутри `lib/`**, где по конвенции ожидаются юнит-тесты, но он на 100% читает `models.ts` и 4 других файла как текст и проверяет regex-ом отсутствие захардкоженных строк модели (`/"claude-(?:sonnet|haiku|opus)-[0-9][^"]*"/`).
- `lib/finance/pnlHonesty.test.mts:1-36` — то же самое: 5 файлов читаются как текст, тесты — сплошные `assert.match`/`assert.doesNotMatch` по именам функций и JSX-фрагментам.

**Почему это плохо**:
1. **Тест не ловит логическую ошибку**, если код по-прежнему содержит нужную подстроку. `assert.match(route, /getOzonCabinetScope/)` пройдёт, даже если функция вызвана с неверными аргументами, в неверном месте или её результат никуда не подставлен.
2. **Тест ломается при чисто косметическом рефакторинге**, не трогающем поведение (переименование, форматирование, перенос компонента в другой файл — ровно то, что уже случилось в `unit-group-ui`, см. §5).
3. **Порядок/расстояние в исходном тексте — хрупкий прокси для порядка исполнения**. `indexOf(...) < indexOf(...)` в `unit-margin-safety.regression.test.mts` (например строки с `cronIndex < guardIndex`) верно ровно до первого форматирования/добавления комментария между блоками.
4. Такие тесты **дорого понимать и чинить**: падение не говорит «функция вернула не то», оно говорит «строка `X` больше не встречается в файле `Y»» — приходится читать сам продукт-код, чтобы понять, что случилось на самом деле (комментарий в `unit-group-ui.test.mts:1-10` — это буквально post-mortem предыдущего такого провала, оставленный в самом тесте).
5. Зелёный `npm test` в этом жанре означает «текст файла соответствует шаблону», а не «фича работает» — то есть половина зелёного гейта — это защита от переименований, а не от багов.

## 4. Три известных провала (regex разошёлся с кодом)

Формулировка задачи называет `full-data-audit-regression`, `unit-group-ui`, `unit-margin-safety` — все три подтверждены как принадлежащие именно этому жанру (текстовые проверки исходников), что и объясняет их хрупкость:

- `unit-group-ui.test.mts:1-13` — комментарий в самом файле документирует причину: тест раньше «считал, что компонент один», после разделения `/unit` и `/opiu/margin` на два разных компонента тест продолжал сторожить не тот файл — т.е. рефактор поведения не менял, а regex перестал соответствовать структуре файлов.
- `unit-margin-safety.regression.test.mts` — часть теста (после строки ~76) держит жёсткие `indexOf`-цепочки по конкретному route-файлу; любое переупорядочивание кода внутри `GET`-хендлера ломает тест без изменения поведения.
- `full-data-audit-regression.test.mts:9-21` — 4 файла читаются как текст и матчатся по именам функций; переименование/инлайн любой из них (`loadWbCachedFinance`, `getOzonCabinetScope`, `fetchReportRows`) ломает тест независимо от корректности результата.

Это системный риск, а не невезение: раз почти треть файлов (92/357) построена по этому шаблону, вероятность, что **следующий безобидный рефакторинг** уронит несколько тестов «ложно-красным», а не поймает реальный баг, довольно высокая — и наоборот, при таком объёме regex-тестов часть настоящих логических ошибок в этих зонах гейт в принципе не может увидеть, потому что тест никогда не вызывает код.

## 5. 128 ошибок `tsc` из-за расширений импорта

Статически подтверждается корневая причина:
- **134 импорта** вида `from "../lib/.../file.ts"` (с явным расширением `.ts`) найдены в 50 тестовых файлах (`grep -c` по `tests`, `lib`, `components`), например `tests/role-permissions.test.mts:14`, `tests/multi-role.test.mts:6-7,15`, `tests/ctr-leader-verdict.test.mts:3`, `tests/agent-mvp-broker.test.mts:11`, `tests/write-off-limit.test.mts:4-5`.
- `tsconfig.json:1-24` использует `"moduleResolution": "bundler"` и **не** включает `"allowImportingTsExtensions": true`. При этой комбинации `tsc` обязан выдавать `TS5097` («An import path can only end with a '.ts' extension when 'allowImportingTsExtensions' is enabled») на каждый такой импорт — отсюда и заявленные ~128 ошибок (134 найденных вхождения — близкое число, разница объяснима повторными импортами из одного и того же модуля/multiline-импортами, посчитанными иначе).
- Ни один штатный скрипт эту ошибку не ловит:
  - `npm test` — гоняет `tsx`, который транспилирует (`esbuild`-семантика), а не типизирует; расширение `.ts` в импорте ему безразлично, тест зелёный.
  - `npm run lint` — ESLint без type-aware конфигурации; `TS5097` — это диагностика компилятора, не ESLint-правило.
  - Явного `tsc --noEmit`/`typecheck` скрипта нет вовсе.
  - `npm run build` (`next build --webpack`) потенциально имеет шанс подтянуть эти файлы под typecheck Next.js, поскольку `tsconfig.json:16-23` включает `**/*.mts` в `include` без исключения `tests/`/`*.test.mts`, а `next.config.ts:1-14` не содержит `typescript.ignoreBuildErrors` — но по правилам аудита сборка не запускалась, так что это вывод из конфигурации, а не наблюдение; проверить командой `npm run build` (не запускалась в рамках этого аудита).

Итог: **128 ошибок `tsc` копятся в тестовых файлах никем не замеченными**, потому что ни один из трёх штатных скриптов (`test`, `lint`, а по имеющимся данным и обычный рабочий процесс, ограниченный `npm run dev`, см. §6) их не выявляет.

## 6. E2E/браузерные тесты

Отсутствуют. `playwright` есть в `devDependencies` (`package.json`, секция `devDependencies`) и упоминается в `package.json`/`package-lock.json`, но реально используется только в двух автономных инструментах сбора данных, не имеющих отношения к тестированию панели:
- `tools/shelf-collector/package.json:1-16` — сборщик цен конкурентов (скрейпинг WB через реальный Chrome, обходит антибот).
- `lib/opiu/browser-collector/package.json:1-14` — сборщик выплат WB/Ozon через видимый браузер.

Ни `playwright.config.*`, ни `*.spec.ts`, ни каталога `e2e/` в репозитории нет. Так же нет ни одной строки, рендерящей React-компонент в тесте (нет `@testing-library/react`/`jsdom` в зависимостях — проверено по `package.json`). Следовательно: **никакой автоматической проверки того, что экран реально рисуется правильно в браузере, не существует** — единственная «визуальная» проверка, судя по памяти проекта, выполняется вручную через Chrome MCP/скриншоты при разработке (см. заметку `finance-panel-worktree-dev-build-gotcha` в памяти пользователя), а не автоматизированным гейтом.

## 7. Области продукта без тестов

Проверка велась поиском упоминаний пути (`app/<dir>/`, `lib/<dir>/`) хоть в одном `*.test.mts`.

**Целые lib-модули без единого теста**: `lib/fal` (`pulid.ts`, 46 строк), `lib/google` (`drive.ts` 79 строк, `folderId.ts`), `lib/lab` (4 файла, ~137 строк — генерация промптов/сториджа для UGC-лаборатории), `lib/signals` (`classify.ts`, 77 строк), `lib/yandex` (`disk.ts`, 57 строк).

**Целые app-разделы (page.tsx) без теста**: `app/abc`, `app/accounts`, `app/card-editor`, `app/price-solver`, `app/product`, `app/trends`, `app/uniquizer`, `app/privacy`, `app/market`, `app/losses` (164 строки, финансовый раздел «Потери»), `app/repricer` (сам экран — при этом `lib/repricer/{evaluate,run,scope}.ts` покрыт 3 тестами), `app/reviews` (компонент `components/reviews` тоже без теста), `app/summary` (119 строк).

**Компонентные каталоги без единого колоцированного или косвенного теста**: `components/access`, `components/accounts`, `components/agent`, `components/analytics`, `components/audit`, `components/pim`, `components/providers`, `components/reviews`, `components/sync`, `components/unit` — то есть даже там, где логика (`lib/`) частично покрыта, UI-слой для доступа, аудита, ролей, PIM и обзоров остаётся полностью неверифицированным автоматически.

**API-поверхность**: из 267 файлов `app/api/**/route.ts` только 114 (43%) хоть раз упомянуты в тестах (обычно как текст для regex, см. §3). Оставшиеся 153 (57%) — включая целые группы `app/api/adverts/{action,bid,bulk,clusters,config,cpm-reco,create,deposit,deposits,minus,rename,rules,rules/run,token}`, `app/api/agent/insights*`, `app/api/audit`, `app/api/auth/{me,status}`, `app/api/cabinet-groups/[id]`, `app/api/cabinets/{[id],scopes}`, `app/api/content/{library,role}`, `app/api/costs/categories`, `app/api/ctrtest/[id]*`, весь `app/api/design/*`, `app/api/finance/loans/{marketplace-facts,schedule}`, весь `app/api/lab/*` — не встречаются ни в одном тесте вообще. Оговорка: часть их бизнес-логики может быть покрыта опосредованно через тестируемые `lib/`-функции, которые роут вызывает, — но сама точка входа (авторизация конкретного роута, разбор query, коды ответа) не верифицирована.

## 8. Что это значит для надёжности гейта

Самое важное найдено не в тестах, а в скрипте, который решает судьбу PR — `scripts/pr-gate.mjs` (261 строка, запускается из `.gitea/workflows/ai-gate.yml:78` как `node scripts/pr-gate.mjs`):

- Скрипт **не содержит ни одного вызова `exec`/`spawn`/`child_process`** (проверено grep'ом) — он никогда не запускает `npm test`, `npm run lint` или `npm run build`. Вся его работа — это regex по путям файлов (`RISK_RULES`, `SAFE_FILE`, `PANEL_SCOPE`, `scripts/pr-gate.mjs:23-40, 68-113`) плюс один HTTP-вызов к внешнему LLM-ревьюеру (`askCockpit`, `scripts/pr-gate.mjs:114+`).
- `.gitea/workflows/deploy.yml:1-9,32-52` запускается **только на push в `main`, уже после мёржа**, и вызывает `vercel deploy --prod` — удалённую сборку на инфраструктуре Vercel. Это не гейт (мёрж уже произошёл), и это не `npm test` — если сборка там и типизирует что-то, обнаруженные проблемы всплывут только постфактум, в проде.
- Единственное документированное человеческое требование к PR в `AGENTS.md:11` — «Перед PR убедись, что `npm run dev` поднимается без ошибок» — то есть даже ручной процесс не требует прогона `npm test`/`npm run lint`/`npm run build`, только запуск dev-сервера.
- Память пользователя (`gitea-ai-gate-gotchas.md`, зафиксировано ранее) уже отмечает, что PR от владельца вообще не гейтятся; данный аудит независимо подтверждает и более сильный факт: **гейт не гоняет тесты и сборку ни для чьих PR** — не только для PR владельца.

Следствие для интерпретации всего, что описано выше в §3–§7: 357 тестов существуют как страховка для разработчика, который явно выполняет `npm test` локально по доброй воле (что подтверждается инструкцией `AGENTS.md:11`, требующей только `npm run dev`, — то есть даже это не гарантировано процессом). Зелёный или красный статус `npm test`:
- **не блокирует автомёрж** («зона Финансы/доки, низкий риск» может влиться при провальных тестах — гейт их не проверяет);
- **не блокирует эскалацию к владельцу** (владелец увидит только вердикт LLM-ревьюера и regex-флаги риска, не «тесты падают»);
- зависит от жанра теста: там, где 26-34% тестов — regex-по-исходнику, даже ручной локальный прогон `npm test` даёт ложное чувство безопасности, потому что тест проверяет форму кода, а не его работу, и вдобавок пропускает 128 ошибок типов, которые в принципе не всплывают ни в одном из трёх официальных скриптов.

Итого: тестовый гейт в этом репозитории — это **необязательная, частично нерелевантная (regex-по-тексту) и невидимая для CI** практика. Реальная защита PR — это (а) файловый allowlist по расширениям/путям, (б) внешний LLM-ревьюер, (в) ручная проверка `npm run dev` разработчиком по желанию. Ни один из этих трёх механизмов не гарантирует, что 357 тестов вообще были запущены, а если и были — треть из них по конструкции не может поймать логическую ошибку, если та не меняет текст файла.
