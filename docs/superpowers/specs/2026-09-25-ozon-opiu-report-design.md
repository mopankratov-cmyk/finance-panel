# Финансовый отчёт Ozon («К выплате») — дизайн

Дата: 2026-09-25. Статус: утверждён в чате (текст + визуальный прототип + пересмотренная
структурная разбивка разделов), ожидает финальной вычитки этого файла.

## 1. Контекст и цель

В финпанели уже есть пункт меню «Финансовый отчёт Ozon» (плейсхолдер, PR #1190) и работающий синк
начислений Ozon в таблицы `ozon_accrual_rows` / `ozon_postings` (PR #1255, крон
`/api/sync/ozon-accruals`, почасовой, бэкфилл 75 дней), а также независимый синк расхода рекламы
Ozon в `ozon_ad_daily` (уже в проде, `/api/sync/ozon-adverts`). Задача этого этапа — построить сам
отчёт поверх уже собранных данных, воспроизводящий по смыслу вкладку «К выплате» из эталонной
Google-таблицы Ozon-кабинетов, в дизайне отчёта ВБ (`OpiuPage.tsx`).

Источник понимания требований: разбор двух реальных копий шаблонной Google-таблицы («Ozon
signature ИП Кучеренко» и «Ozon signature ИП Панкратов») в этой же сессии, утверждённый в чате
визуальный прототип (Design-артефакт `UkeHNJJzpmympHBLkFZgSL`), и — что оказалось решающим —
прямая сверка с уже написанным и работающим кодом синка (`lib/ozon/accrualRows.ts`,
`lib/ozon/adDailyMarkers.ts`), а не только с текстом Google-таблицы.

## 2. Почему разбивка по разделам строится из кода, а не из названий в таблице

Первая версия этого дизайна пыталась сопоставить разделы отчёта («Комиссия», «Логистика»,
«Реклама») со списком русских названий категорий из Google-таблицы. От этого пришлось отказаться
по трём причинам, обнаруженным в этой же сессии:

1. Список категорий «Реклама» **не совпадает** между двумя реальными таблицами (Кучеренко:
   Продвижение в поиске, Трафареты, Генерация видеообложки…; Панкратов: Продвижение бренда,
   Звёздные товары, Вывод в топ…) — жёстко фиксировать список по одному примеру означает потерять
   категории, которых в примере просто не случилось.
2. Русские названия в Google-таблице — это перевод из **старого**, уже отключённого 2026-09-08
   API. Новый API Ozon (`/v1/finance/accrual/types`) отдаёт имена в другом виде (например,
   `SaleCommission` для комиссии, id 69 — единственная пара `type_id → имя`, которая точно известна
   из уже написанного кода синка). Сопоставлять русские названия из старой таблицы с id из нового
   API напрямую — гадание, не факт.
3. Одна из формул в самой Google-таблице (D13, «Заказы» внутри «Продажи») оказалась сломана —
   ссылается на текст совершенно другой строки (см. §7). Значит опираться на текст формул
   Google-таблицы как на эталон истины небезопасно без проверки каждой ячейки.

**Решение:** разбивка по разделам строится не по названиям, а по **структуре данных, которую уже
пишет наш собственный код**. Она не требует ни справочника категорий, ни ручной карты, ни
угадывания — только то, что уже проверено и работает в проде.

## 3. Структурные правила разбивки (проверено по коду синка)

`lib/ozon/accrualRows.ts` (`flattenOzonAccrual`, уже в проде) кладёт в `ozon_accrual_rows` только
три вида строк, и это единственные источники всех POSTING/ITEM/NON_ITEM-строк:

- **`accrued_category = "POSTING"`, `type_id = 69`** — синтетическая строка комиссии
  (`OZON_ACCRUAL_SALE_COMMISSION_TYPE_ID`, константа уже существует в коде синка). Всегда и только
  комиссия за продажу.
- **`accrued_category = "POSTING"`, `type_id ≠ 69`** — построчно из `product.delivery.services[]`
  (см. `flattenOzonAccrual`). По построению кода это ВСЕГДА услуги доставки/логистики — не
  предположение о названии, а факт того, из какого места ответа Ozon эта строка взята.
- **`accrued_category = "ITEM"`** — из `item_fees.fees[]`, услуги на уровне конкретного товара, не
  привязанные к отправлению.
- **`accrued_category = "NON_ITEM"`** — из `non_item_fee`, платежи не по конкретному товару и не по
  отправлению (примеры из таблиц: Ozon Рассрочка, Подписка Premium Plus, Эквайринг).

Реклама Ozon **не входит** в `finance/accrual/by-day` вообще — это отдельный API (Ozon
Performance), уже синкается в `ozon_ad_daily` (`client_id`, `sku`, `date`, `spent`,
`orders_money`) через `/api/sync/ozon-adverts`. В этой таблице уже есть готовая, безопасная сумма
за день на весь кабинет — строка с `sku = '*'` (`OZON_AD_CABINET_TOTAL_SKU`,
`lib/ozon/adDailyMarkers.ts`), специально заведённая, чтобы не задваивать расход суммированием по
товарам (комментарий в файле: «обе строки НИКОГДА не участвуют в разрезе по товарам»). Это и есть
источник для раздела «Реклама».

## 4. Разделы отчёта и источники (пересмотрено, заменяет прежнюю версию)

| Раздел | Источник | Правило |
|---|---|---|
| Заказы | `ozon_postings.status` через `describeOzonPostingStatus()` | группировка по `stage` (shipping/transit/delivered/cancelled) |
| Продажи | `ozon_postings.amount` | «Заказы» = Σ`amount` всех отправлений периода; «Возвраты и отмены» = Σ`amount` отправлений со `stage === "cancelled"`, со знаком минус. **Не** из начислений — см. §7, почему |
| Себестоимость | — (заглушка) | текст «не подключено», не входит в итог; отдельная задача, источника для Ozon пока нет |
| Комиссия за продажу | `ozon_accrual_rows` | `accrued_category = "POSTING" AND type_id = 69` |
| Логистика | `ozon_accrual_rows` | `accrued_category = "POSTING" AND type_id ≠ 69`, сворачиваемая детализация по `type_id` |
| Реклама | `ozon_ad_daily` | `sku = '*'` (`OZON_AD_CABINET_TOTAL_SKU`), Σ`spent` за период по выбранным кабинетам |
| Прочие удержания | `ozon_accrual_rows` | `accrued_category IN ("ITEM", "NON_ITEM")`, сворачиваемая детализация по `type_id` |
| К выплате | Σ Продажи + Комиссия + Логистика + Реклама + Прочие удержания | Себестоимость не входит (заглушка) |

Каждое правило проверяемо по уже существующему коду (не по тексту Google-таблицы) — новый
`type_id`, который Ozon пришлёт впервые, автоматически попадает в правильный раздел по
`accrued_category`, без ручной разметки.

## 5. Имена строк внутри «Логистика» / «Прочие удержания» — best-effort, не критичны для суммы

Сумма каждого раздела корректна и без знания человекочитаемых названий отдельных `type_id`
(правило §3 — структурное, не по имени). Но для удобства чтения хочется подписывать строки
детализации не числом `type_id`, а названием. Для этого:

- Таблица `ozon_accrual_types` — кэш `/v1/finance/accrual/types` (`type_id`, `name`, `description`).
  Обновляется раз в сутки (см. §8, отдельный крон-роут).
- В детализации `type_id`, для которого нет строки в кэше (ещё не обновлялся, или Ozon только что
  завёл новый) — подписывается как `Категория #<type_id>`, сумма всё равно учтена и в разделе, и в
  итоге. Это не баннер-предупреждение (см. §6) — это просто резервная подпись строки, отчёт из-за
  неё не ломается.

## 6. Видимость новых категорий в интерфейсе

Требование пользователя: «нужно чтобы было видно в интерфейсе». Раз разбивка по разделам теперь
структурная (§3), а не по ручной карте, случая «категория никуда не попала» больше не существует —
но человеку всё равно полезно знать, когда внутри «Прочие удержания» (самого широкого раздела)
appeared совсем новый `type_id`, которого не было ни разу за последние 30 дней до начала периода
отчёта, — просто как сигнал «на что стоит взглянуть», не как ошибку.

Баннер над таблицей (см. прототип): «Ozon прислал начисление по новой категории (`Категория #123`
или её имя, если есть в кэше §5) — учтено в «Прочих удержаниях» и в итоге полностью, взгляните,
не нужна ли отдельная подпись». Ненавязчивый, не блокирует отчёт.

## 7. Почему «Продажи» не тянется из начислений

При проверке формул Google-таблицы напрямую (не только по значениям) обнаружена изолированная
аномалия: ячейка D13 («Заказы» внутри «Продажи») ссылается на `$C19` («Доставка покупателю» —
чужая строка из блока «Себестоимость»), а не на свою `$C13`. Соседние D14 и D16 проверены и
корректно ссылаются сами на себя — это одна конкретная опечатка в конкретной таблице-примере, не
системная проблема формата, но она означает, что нельзя доверять этой конкретной формуле как
эталону того, что должно суммироваться в «Заказы».

Вместо того чтобы гадать, какой `type_id`/категория начислений должна была иметься в виду,
раздел «Продажи» в этой реализации строится из уже надёжного источника — самих отправлений
(`ozon_postings.amount`, см. §4). Это не копия оригинальной таблицы построчно, а честная замена той
её части, которая не может быть проверена как правильная.

## 8. Кэш справочника категорий — реализация

`ozonAccrualTypes()` (`lib/ozon/api.ts:506-522`) сейчас — только живой запрос к Ozon, нигде не
сохраняется, нулевые вызовы в кодовой базе.

- Таблица `ozon_accrual_types` (`type_id` int PK, `name` text, `description` text, `updated_at`
  timestamptz).
- Справочник кабинето-независим (это категории Ozon вообще, не конкретного продавца) — обновляется
  раз в сутки отдельным лёгким крон-роутом, который берёт **любой** активный Ozon-кабинет для
  авторизации запроса (сами данные от кабинета не зависят).

## 9. Период

Единственный режим выбора периода — произвольный диапазон `dateFrom`/`dateTo` (упрощено в чате:
никакой «даты отчёта» со скользящими неделями, в отличие от ВБ-отчёта). Один столбец сумм на весь
диапазон.

## 10. API

`GET /api/opiu/ozon?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD&cabinetIds=…`

- Права: переиспользуем `finance.view`/`finance.edit` (та же матрица, что у `/api/opiu`), новая
  запись в `lib/auth/apiPermissions.ts`.
- Валидация дат — тем же `isValidDateParam`, что у ВБ-отчёта (`lib/opiu/weeks.ts`).
- Ответ: список секций `{ key, label, kind: "metric" | "stub", value, children?: { label, value,
  typeId }[] }` в порядке §4, плюс `newCategories: { typeId, label }[]` (§6) и `total`.

## 11. UI

`OzonOpiuPage.tsx` — из плейсхолдера в полноценный клиентский компонент:

- Верхний блок фильтров: `dateFrom`/`dateTo`, мультиселект кабинетов Ozon (данные — из уже
  существующего `GET /api/cabinets`, отфильтрованные на клиенте по `marketplace === "ozon"`,
  отдельный эндпоинт не нужен), кнопка «Обновить» — визуально как в отчёте ВБ.
- Баннер новых категорий (§6) — жёлтый, ненавязчивый, над таблицей, только когда есть что
  показать.
- Таблица: один столбец сумм (без закреплённого прокручиваемого столбца — не нужен без
  понедельной разбивки). Крупные статьи — цветные строки (синие для доходной части, розовые для
  расходной, как в ВБ-отчёте и в исходной Google-таблице), раскрывающаяся по клику детализация для
  Логистики и Прочих удержаний, статус-заглушка для Себестоимости, итоговая строка «К выплате».
- Визуальный прототип: `https://claude.ai/artifact/UkeHNJJzpmympHBLkFZgSL` (утверждён в чате; числа
  внутри разделов Логистика/Реклама в прототипе иллюстративные, реальная разбивка теперь по §4, не
  по именам из прототипа).

## 12. Вне рамок этого этапа

- Реальный расчёт «Себестоимость» для Ozon (нужен отдельный источник — себестоимость по SKU,
  аналог `product_costs`, но под Ozon-номенклатуру). Отдельная задача.
- «Маржа по артикулам Ozon» — отдельный пункт меню, отдельная задача.
- Ручная/автоматическая карта «категория → более гранулярная подстатья» внутри «Логистика» или
  «Прочие удержания» (например, отдельно показать «сборку» и «последнюю милю») — не требуется для
  первой версии: структурная разбивка по разделам (§3) уже корректна и полна, более тонкая разбивка
  — будущее улучшение, не блокирующее эту задачу.

## 13. Риски / открытые вопросы для плана реализации

- **Закрыто.** `ozon_postings.amount` (§4, §7) проверено по коду (`lib/ozon/api.ts`,
  `postingFromUnknown`): `amount = Σ(product.price × product.quantity)` по товарам отправления —
  это именно сумма продажи, а не логистическая или комиссионная составляющая. Источник для
  «Продажи» подтверждён.
- Раздел «Реклама» в собранном отчёте не имеет внутренней детализации по рекламным кампаниям в
  этой версии (только общая сумма из `ozon_ad_daily` с `sku = '*'`) — это соответствует
  утверждённому прототипу (там тоже был единый агрегат с примерной детализацией, которая по факту
  не будет использоваться, раз источник данных не даёт деления по названиям кампаний в этом
  разрезе без отдельного запроса). Если в будущем понадобится реальная детализация трат по
  рекламным инструментам — отдельная задача поверх Ozon Performance API.
- Обнаружение «новых» категорий (§6) технически — просто `type_id`, отсутствующий в `ozon_accrual_types`
  на момент построения отчёта, среди `type_id`, встретившихся в `ozon_accrual_rows` за период —
  подтверждается на этапе плана простым JOIN/anti-join, без отдельного кэша «видели ли вчера».
