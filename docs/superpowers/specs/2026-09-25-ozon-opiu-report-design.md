# Финансовый отчёт Ozon («К выплате») — дизайн

Дата: 2026-09-25. Статус: утверждён в чате (текст + визуальный прототип), ожидает вычитки этого файла.

## 1. Контекст и цель

В финпанели уже есть пункт меню «Финансовый отчёт Ozon» (плейсхолдер, PR #1190) и работающий синк
начислений Ozon в таблицы `ozon_accrual_rows` / `ozon_postings` (PR #1255, крон
`/api/sync/ozon-accruals`, почасовой, бэкфилл 75 дней). Задача этого этапа — построить сам отчёт
поверх уже собранных данных, воспроизводящий по смыслу вкладку «К выплате» из эталонной
Google-таблицы Ozon-кабинетов, в дизайне отчёта ВБ (`OpiuPage.tsx`).

Источник понимания требований: разбор двух реальных копий шаблонной Google-таблицы («Ozon
signature ИП Кучеренко» и «Ozon signature ИП Панкратов») в этой же сессии, плюс утверждённый в
чате визуальный прототип (Design-артефакт `UkeHNJJzpmympHBLkFZgSL`).

## 2. Ключевая находка: `SUMIFS` по категории — это `GROUP BY type_id`

Формула каждой строки вкладки «К выплате» — `SUMIFS(сумма; дата; >=период; дата; <=период;
тип_услуги; ="название_строки")`. Вкладка-источник («Список начислений») — устаревший широкий
формат экспорта Ozon (одна строка на отправление, десятки колонок под конкретные типы комиссий),
привязанный к уже отключённому 2026-09-08 API. Наш `ozon_accrual_rows` уже хранит те же данные в
удобном «длинном» формате (`type_id`, `amount`, `date`) — репликация формулы сводится к `GROUP BY
type_id, SUM(amount) WHERE date BETWEEN …`.

## 3. Важное расхождение между двумя реальными таблицами — источник требования №1

Список категорий раздела «Реклама» в таблице Кучеренко (Продвижение в поиске, Трафареты,
Генерация видеообложки, Забытые товары…) **не совпадает** со списком в таблице Панкратова
(Продвижение бренда, Звёздные товары, Вывод в топ, Оплата за клик…). Это прямое доказательство,
что жёстко фиксировать список категорий по одному примеру — ошибка: наберётся неполный список, и
Ozon любого кабинета неизбежно начислит что-то, чего в списке нет.

**Следствие для архитектуры:** список категорий отчёта не может быть построен по одной
Google-таблице-примеру. Он должен строиться из справочника Ozon `/v1/finance/accrual/types`
(`lib/ozon/api.ts:ozonAccrualTypes()`, ~124 записи, id+name+description) и из фактически
пришедших `type_id` в `ozon_accrual_rows` — то есть данные ведут разметку, а не наоборот.

## 4. Раздел «Прочие удержания» — не список, а остаток

В обеих таблицах раздел «Прочие удержания» (не «начисления» — исправлено по замечанию в чате)
содержит 100+ отдельных строк-категорий и продолжается далеко за пределы того, что разумно
перечислять вручную. По смыслу это не отдельный список, а «всё, что не попало в явно
поименованные разделы» — technically остаток. В нашей реализации это не список условий, а
арифметический остаток: `Прочие удержания = Σ(amount по всем type_id) − Σ(amount по type_id,
явно отнесённым к другим разделам)`. Это гарантирует (см. §5), что даже неразмеченная категория
не исчезает из общей суммы.

## 5. Данные никогда не теряются — даже для ещё не размеченной категории

Обсуждено в чате явно (см. §3): что происходит, когда Ozon вводит новую категорию начислений,
которой нет в карте «категория → раздел»?

- **Синк** (`flattenOzonAccrual`, уже в проде) не фильтрует по известным `type_id` — новая
  категория попадает в `ozon_accrual_rows` как есть, независимо от того, знает ли о ней отчёт.
- **Итог «К выплате»** считается как сплошная сумма по ВСЕМ строкам периода (не «сумма по
  известным категориям») — новый `type_id` учтён в итоге с первого дня появления, до того как
  кто-то явно отнесёт его к разделу.
- **Раздел** для неразмеченной категории — безопасный дефолт «Прочие удержания» (см. §4), никогда
  не «нигде».
- **Видимость** (требование пользователя: «нужно чтобы было видно в интерфейсе») — отчёт
  сравнивает набор `type_id`, встретившихся за период, с картой «категория → раздел». Всё, что
  встретилось, но не размечено, показывается баннером над таблицей: «Ozon прислал начисления по
  категории «X» — такой категории ещё нет в разметке разделов. Сумма учтена в «Прочих
  удержаниях» и в итоге полностью, но раздел стоит уточнить» (см. прототип). Баннер — не
  блокирующий, отчёт полностью функционален и без разметки; это подсказка, а не ошибка.

## 6. Новая таблица: кэш справочника категорий

`ozonAccrualTypes()` (`lib/ozon/api.ts:506-522`) сейчас — только живой запрос к Ozon,
нигде не сохраняется, нулевые вызовы в кодовой базе. Нужна:

- Таблица `ozon_accrual_types` (`type_id` PK, `name`, `description`, `updated_at`).
- Обновление раз в сутки достаточно (справочник у Ozon меняется редко, `revalidate: 86400` уже
  стоит на живом вызове) — отдельный лёгкий крон-роут или обновление синхронно при следующем
  прогоне `/api/sync/ozon-accruals`, если там уже есть подходящее место. Решается на этапе плана.
- Имя категории (`name`) нужно и для баннера (§5), и потенциально для будущей более гранулярной
  детализации внутри разделов.

## 7. Карта «категория → раздел»

Простой конфиг в коде (`lib/ozon/accrualReportSections.ts` или аналог), НЕ автогенерируемый из
таблицы-примера:

```
type SectionKey = "commission" | "logistics" | "ads" | "other";
type_id → SectionKey  (или "не размечено" → "other" по умолчанию)
```

- Заполняется вручную по мере появления реальных данных (используя `name` из справочника Ozon как
  подсказку — оператор смотрит на баннер и добавляет строку в карту).
- Никогда не выбрасывает данные — отсутствие записи означает «other», не ошибку.
- Раздел «Комиссия за продажу» в изученных таблицах не имел вложенной детализации (одна сумма) —
  в нашей версии оставляем так же: несколько `type_id` могут относиться к `"commission"`, но
  детализация внутри раздела не показывается (только реальный `type_id` список используется для
  корректной суммы, UI показывает один агрегат).

## 8. Разделы отчёта и источники (утверждено в прототипе)

| Раздел | Источник | Заметки |
|---|---|---|
| Заказы | `ozon_postings.status`, через уже существующий `describeOzonPostingStatus()` | количество/сумма по статусам (Доставлено/Отменено/Доставляется/Ожидает отгрузки/Ожидает упаковки); **не** из начислений |
| Продажи | `ozon_accrual_rows`, вероятно тоже `SUMIFS`/`GROUP BY type_id` по 5 конкретным категориям (заказы/возвраты/доставка-обработка возврата/получение возврата/отмена начисления доставки) — **формула не проверена напрямую**, проверена только для «Эквайринга» (см. §13) | всегда развёрнуто (короткий список, как в исходной таблице) |
| Себестоимость | — (заглушка) | текст «не подключено», не входит в итог; источник (себестоимость по SKU для Ozon) появится отдельной задачей |
| Комиссия за продажу | `ozon_accrual_rows` по карте (§7) | один агрегат, без детализации |
| Логистика | `ozon_accrual_rows` по карте (§7) | сворачиваемая детализация по `type_id`, свёрнуто по умолчанию |
| Реклама | `ozon_accrual_rows` по карте (§7) | сворачиваемая детализация; список **не хардкодится**, строится из реально пришедших `type_id`, отнесённых к разделу |
| Прочие удержания | остаток (§4) | сворачиваемая детализация; сюда же падают неразмеченные категории (§5) |
| К выплате | Σ всех строк периода, кроме Себестоимости | итог, всегда полный, независимо от разметки |

## 9. Период

Единственный режим выбора периода — произвольный диапазон `dateFrom`/`dateTo` (упрощено в чате:
никакой «даты отчёта» со скользящими неделями, в отличие от ВБ-отчёта). Один столбец сумм на весь
диапазон. У начислений Ozon нет отдельного понятия «дата продажи» — фильтр только по
`ozon_accrual_rows.date` / `ozon_postings.created_at`.

## 10. API

`GET /api/opiu/ozon?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD&cabinetIds=…`

- Права: переиспользуем `finance.view`/`finance.edit` (та же матрица, что у `/api/opiu`), новая
  запись в `lib/auth/apiPermissions.ts`.
- Валидация дат — тем же `isValidDateParam`, что у ВБ-отчёта.
- Ответ: плоский список строк `{ key, label, kind: "metric" | "stub" | "child", value, sectionKey,
  parentKey? }` плюс `newCategories: { typeId, name, sampleSection: "other" }[]` для баннера (§5) и
  `total`.

## 11. UI

`OzonOpiuPage.tsx` — из плейсхолдера в полноценный клиентский компонент:

- Верхний блок фильтров: `dateFrom`/`dateTo`, мультиселект кабинетов Ozon, кнопка «Обновить» —
  визуально как в отчёте ВБ.
- Баннер новых категорий (§5) — жёлтый, ненавязчивый, над таблицей, только когда есть что
  показать.
- Таблица: один столбец сумм (без закреплённого прокручиваемого столбца — он не нужен без
  понедельной разбивки, упрощение относительно ВБ-отчёта). Крупные статьи — цветные строки (синие
  для доходной части, розовые для расходной, как в ВБ-отчёте и в исходной Google-таблице),
  раскрывающаяся по клику детализация для Логистики/Рекламы/Прочих удержаний, всегда развёрнутая
  для Продаж, статус-заглушка для Себестоимости, итоговая строка «К выплате».
- Визуальный прототип: `https://claude.ai/artifact/UkeHNJJzpmympHBLkFZgSL` (утверждён в чате после
  двух раундов правок).

## 12. Вне рамок этого этапа

- Реальный расчёт «Себестоимость» для Ozon (нужен отдельный источник — себестоимость по SKU,
  аналог `product_costs`, но под Ozon-номенклатуру). Отдельная задача.
- «Маржа по артикулам Ozon» — отдельный пункт меню, отдельная задача, не пересекается напрямую с
  этим отчётом.
- Автоматическая (не через оператора) классификация новых категорий по ключевым словам в `name` —
  можно рассмотреть как будущее улучшение, не требуется для первой версии: баннер + ручная правка
  карты — достаточно, и предсказуемее эвристики.

## 13. Риски / открытые вопросы для плана реализации

- Где физически обновлять `ozon_accrual_types` (свой крон-роут или довесок к существующему
  `/api/sync/ozon-accruals`) — решить на этапе плана, с тем же принципом «один кабинет/один запрос
  за прогон» (сам справочник кабинето-независим, так что может быть проще: раз в сутки, без
  привязки к кабинету).
- Формулы строк «Продажи» (D13-D17 в изученных таблицах) проверены только визуально по значениям,
  не по тексту формулы (в отличие от «Эквайринга», где формула прочитана напрямую, см. §2). Перед
  тем как писать SQL/группировку для этого раздела, стоит открыть исходную таблицу ещё раз и
  прочитать формулы этих пяти ячеек — возможно, «Заказы»/«Возвраты и отмены» считаются не по
  `type_id`, а по данным заказов/отправлений (ближе к разделу «Заказы», чем к начислениям).
- Обнаружение «новых» категорий (§5) технически — просто `type_id`, отсутствующий в карте (§7),
  среди `type_id` за запрошенный период; отдельный кэш «видели ли мы это вчера» не обязателен для
  первой версии — баннер может показываться каждый раз, пока категорию не добавят в карту
  (это самоочищающееся условие: как только запись появится в карте, баннер по этой категории
  исчезнет сам).
