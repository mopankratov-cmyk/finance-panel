# ТЗ: Условия приёма зарплатной ведомости в репозиторий

> База кода: ветка от **gitea/main**. Читать до старта: `docs/DDS-RULES.md` целиком, `lib/finance/categories.ts`, `lib/finance/factLinks.ts`, `components/calendar/calendarPlan.ts`.
> Контекст: модуль «Зарплатная ведомость» существует локально у сотрудника (7 действующих + 80 уволенных, оклады, виды оформления, налоги, начисления 5-го и 20-го, реквизиты, телефоны) — в репозитории его нет ни строки. Этот файл — не «как написать модуль», а **чему он обязан соответствовать, чтобы быть влитым**, и в каком порядке заезжать.

## 0. Инструкция исполнителю (читать первым)
- Первый PR — **только схема и просмотр** (§7, шаг 1). Ни одного пути записи в `payments`.
- Персональные данные (реквизиты, телефоны, паспорт) — отдельная таблица, отдельный роут, отдельная проверка роли. Не в `payments.comment`, не в `companies`, не в JSON внутри сотрудника.
- Всё, что закрывает обязательство фактом ДДС, — через `lib/finance/factLinks.ts` (I1) и только с ручным подтверждением (I2). Автозакрытия долга нет вообще — не «по умолчанию выключено», а отсутствует как код.
- Зона МОЖНО (§4) — новые каталоги. Правки в существующие файлы ДДС — только те, что перечислены в §6; любые другие — стоп и отчёт.

## 1. Цель и наблюдаемое поведение
- Раздел `/payroll` (роль `director`, `finance`): справочник сотрудников (без реквизитов в таблице), начисления по датам, задолженность по сотруднику = начислено − подтверждённые выплаты.
- Начисление создаёт **плановый** платёж в календаре со статьёй из справочника (`Зарплата административного персонала` / `…коммерческого…` / `…производственного…`) и меткой `[payroll:<accrualId>]`.
- Найденный в ДДС факт выплаты **предлагается** к сопоставлению; человек вручную распределяет сумму между «текущая зарплата», «долг текущего года», «долг прошлых лет» и подтверждает. До подтверждения ничего не меняется.
- Карточка сотрудника: история начислений, выплат, остатков — по данным подтверждённых распределений.
- Реквизиты и телефоны — отдельная защищённая вкладка, видна только `director`, в экспорт/Google не уходит.

## 2. Решения приняты за тебя
- Таблицы: `payroll_employees` (id, full_name, employment_type, status active/dismissed, hired_at, dismissed_at, salary_rub, payment_method, tax_mode, company_id, created_at), `payroll_accruals` (id, employee_id, period_month, accrual_date, amount_rub, kind salary/advance/bonus/debt_carry, planned_payment_id → payments.id null, created_at), `payroll_allocations` (id, accrual_id, payment_id → payments.id, amount_rub, bucket current/debt_current_year/debt_prior_years, confirmed_by, confirmed_at), `payroll_employee_private` (employee_id pk, bank_details, phone, passport_ref; RLS; читает только роут с `requireApiSession(["director"])`).
- Уникальность: `payroll_allocations (payment_id, accrual_id)`; сумма allocations по `payment_id` ≤ `|payments.amount|` — проверяется в роуте, не только в UI.
- Статьи — только из `lib/finance/categories.ts`; новых литералов нет. Если нужна «Аванс по зарплате» — одна строка в `REGISTRY`, отдельным PR.
- Импорт справочника из Excel — через `readFirstSheetXlsx` из `components/payments/bankStatement.ts` (уже есть), с предпросмотром и счётчиком пропущенных строк (как в #868).
- Факты для сопоставления — только `status === "done"`, `amount < 0`, не занятые (`consumedFactIds`), статья из группы «Зарплата…» или контрагент, совпавший с ФИО. Совпадение показывается, не применяется.
- Никакого «закрыть долг автоматически по сумме». Кнопка «Подтвердить распределение» — единственный путь записи в `payroll_allocations`.

## 7. Порядок шагов (три PR)
1. **PR-A (к владельцу):** миграция §2 + `lib/payroll/model.ts` (типы, `employeeDebt()` чистая функция) + тесты + страница `/payroll` в режиме **только чтение** с импортом справочника в предпросмотр (ничего не сохраняет). Цель — владелец видит 87 сотрудников и цифры до того, как модуль начнёт писать.
2. **PR-B:** сохранение справочника и начислений; плановые платежи в календарь через `/api/finance/state` (обычный `ADD_PAYMENT`) с меткой `[payroll:<id>]`; частная вкладка реквизитов.
3. **PR-C:** сопоставление с фактами ДДС: предложение → ручное распределение → `payroll_allocations`; метка `[payroll-paid:]`; отображение в карточке сотрудника. Гейт + ручная проверка: один факт нельзя распределить дважды; распределение больше суммы факта отклоняется роутом.

## 8. Что НЕ делать
Не писать в `payments` напрямую из роутов зарплаты (только через существующий `/api/finance/state`); не хранить реквизиты в `comment`/JSON; не выгружать частные данные в Google; не добавлять авто-сопоставление «по сумме и дате»; не менять форматы существующих меток.

## 9. Гейт
```
npm test                 # baseline 03.09.2026: # pass 1485 / # fail 0 → ≥ 1485 + свои
npx tsc --noEmit
npx eslint <изменённые>
```
Тесты обязательны: `employeeDebt` (начислено − подтверждённые; неподтверждённые не уменьшают долг); роут распределения отклоняет сумму > факта и повторное использование факта; частный роут отдаёт 403 для `finance`.

## 10. Стоп-условия и отчёт
Стоп: нужна правка вне §4/§6; в локальной версии есть путь автозакрытия долга — он не переносится, а описывается в отчёте; гейт красный после 3 попыток.
