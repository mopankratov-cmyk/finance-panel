# Доступ команды + двухуровневое одобрение PR — чеклист владельца

## Короткая схема
Для сотрудников и для владельца здесь один путь:

`ветка → PR → ai-gate → approve = auto-merge + deploy, escalate = ручная проверка`

Разница только в том, кто видит эскалацию. Сотрудник всегда работает через свою ветку и PR, а не напрямую в `main`.

Сотрудники дорабатывают панель через Claude Code. Каждый PR проходит **двухуровневый гейт**:

```
Сотрудник → PR
   │
   ▼
GitHub Action «ai-gate» (pull_request_target: код PR НЕ исполняется,
   дифф/файлы берутся из GitHub API; гейт = доверенный скрипт базовой ветки)
   │
   ├─ approve: ВСЕ файлы — доки/текст/картинки + ассистент одобрил
   │            ──► авто-мёрж (squash) в main ──► Vercel деплоит прод
   │                (тебе в Telegram «✅ влил PR #N»)
   │
   └─ escalate: затронут код/конфиг, либо риск/форк/большой дифф, либо ассистент не одобрил
                ──► чек КРАСНЫЙ (сотрудник влить не может) + Telegram «⚠️ проверь PR #N»
                ──► мержишь ты (bypass) ──► деплой
```

**Авто-мёрж только для «безопасного» = allowlist** (`.md/.txt/картинки`, без удалений, не из форка).
**Любой код или конфиг всегда уходит к тебе** — это осознанно консервативно. Дополнительно детектор в
`scripts/pr-gate.mjs` маркирует классы высокого риска (миграции/БД, `.env`, зависимости, CI, деплой-конфиг,
auth/оплата, `.mjs/.sh`, Dockerfile…) для понятного «почему эскалировали».

### Что уже в коде
- `finance-panel`: `.github/workflows/ai-gate.yml` (триггер `pull_request_target` — безопасно) + `scripts/pr-gate.mjs` (allowlist-гейт); `.github/CODEOWNERS`, `.github/pull_request_template.md`.
- `director-cockpit`: `app/api/review/route.ts` — ревью-маршрут (строгий JSON-вердикт, авторизация отдельным `REVIEW_TOKEN`, дифф как недоверенный ввод, свой бюджет помимо личного `$5`-лимита).

> Почему `pull_request_target`, а не `pull_request`: при `pull_request` GitHub исполнил бы копию воркфлоу и скрипта **из самого PR** — сотрудник переписал бы гейт и сам себя одобрил + получил бы секреты. `pull_request_target` запускает код **базовой ветки**, а изменения PR читает как данные через API.

## 1. Пригласить сотрудников
Settings → Collaborators → **Add people** → роль **Write** (могут пушить ветки и открывать PR, но не вливать в защищённый `main`).
```bash
gh api -X PUT repos/mopankratov-cmyk/finance-panel/collaborators/<ник> -f permission=push
```

## 2. director-cockpit — поднять ревьюера
Маршрут `/api/review` уедет в прод со следующим пушем `director-cockpit`. В его Vercel-окружении задай:
- `ANTHROPIC_API_KEY` (ревью думает им),
- `REVIEW_TOKEN` — **новый отдельный секрет** (придумай длинную случайную строку). По нему авторизуется Action — так мастер-`CRON_SECRET` в GitHub не попадает.
- (опц.) `MACHINE_DAILY_USD_CAP` — потолок трат на машинные ревью (CI не упрётся в твой личный `CLAUDE_DAILY_USD_CAP`, но и не разгонит счёт без предела).

Проверка после деплоя:
```bash
curl -s -H "Authorization: Bearer <REVIEW_TOKEN>" https://director-cockpit.vercel.app/api/review
# → {"ok":true,"route":"review","ready":true,"model":"claude-sonnet-4-6"}
```

## 3. finance-panel — секреты Action
Settings → Secrets and variables → **Actions** → New repository secret:

| Имя | Значение |
|---|---|
| `REVIEW_TOKEN` | та же случайная строка, что задал в director-cockpit (шаг 2) |
| `TELEGRAM_BOT_TOKEN` | бот @mkt_aibot |
| `TELEGRAM_ALERT_CHAT_ID` | id твоей лички |
| `DIRECTOR_COCKPIT_URL` | опц., по умолчанию `https://director-cockpit.vercel.app` |

## 4. Разрешить авто-мёрж
Settings → General → Pull Requests → ✅ **Allow auto-merge**, ✅ **Allow squash merging**.
(Без «Allow auto-merge» шаг авто-влития approve-PR упадёт.)

## 5. Защитить `main` (это и есть бэкстоп — без него escalate сотрудник сможет влить сам)
Settings → **Rules → Rulesets → New branch ruleset**:
- Target: `main`
- ✅ Restrict deletions, ✅ Block force pushes
- ✅ Require a pull request before merging (approvals: **0** — гейтом служит статус-чек, а не счётчик ревью)
- ✅ Require status checks to pass → добавь **`ai-gate`**
  *(чек появится в списке после первого прогона — открой тестовый PR, затем вернись и отметь его)*
- **Bypass list: добавь СЕБЯ** — чтобы вливать escalate-PR с красным чеком после своей проверки.
- ❌ НЕ включай «Require branches to be up to date» (иначе постоянные ребейзы) и НЕ требуй Code Owners review (заблокирует авто-мёрж).

**Доп. защита гейта (рекомендую):** заведи второй ruleset, запрещающий не-владельцу менять файлы гейта —
`.github/**` и `scripts/pr-gate.mjs` (Rules → Rulesets → восстановление пути / «Restrict file paths» либо
required review только на эти пути). Гейт и так помечает изменения этих файлов как «код → к тебе» (авто-мёрж их
не вольёт), но запрет на уровне правил — жёсткий замок: даже PR, меняющий сам гейт, нельзя протащить мимо тебя.

## 6. Ключи сотрудникам — через менеджер паролей (основной способ)
Секретов в git нет (`.env*` в `.gitignore`). Раздаём dev-`.env.local` через **1Password / Bitwarden Send** (с TTL), **не открытым текстом**.
- Заведи **отдельные dev-ключи** (урезанные, с лимитами), а не боевые на чужих ноутах — утечка тогда = отзыв одного дев-ключа.
- Отзыв доступа = ротнуть dev-ключи (+ убрать из GitHub/Vercel).

**Vercel — добавляешь сотрудников как `Viewer` (бесплатно).** Это даёт им только просмотр превью-деплоев их PR. Значения env Viewer **не видит** и `vercel env pull` сделать **не может** — поэтому ключи идут через менеджер паролей, а не из Vercel.
> Если когда-нибудь захочешь, чтобы сотрудник тянул env сам (`vercel env pull`), нужна платная роль **Member** (~$20/мес за место). Для текущей схемы не требуется.

**Новые переменные окружения от сотрудников.** Сотрудник (Viewer) **не может** добавить env в Vercel. Процесс:
1. Он добавляет имя переменной (с заглушкой) в `.env.example` и флажок в описании PR.
2. **Ты** заводишь реальное значение в Vercel → Settings → Environment Variables, в нужных окружениях (Production / Preview / Development) — до мёржа/деплоя.
3. Если переменная нужна и сотруднику локально — пришли ему значение через 1Password/Bitwarden, он положит в свой `.env.local`.

Гейт всё равно эскалирует тебе любой PR, трогающий `.env*` или код с новой переменной, так что мимо тебя это не пройдёт.

> ⚠️ `.env.example` теперь трекается (`!.env.example` в `.gitignore`) — **перед первым коммитом открой его и убедись, что внутри только заглушки, без реальных значений** (я его прочитать не могу — `.env*` под защитой прав). Дальше добавь его в git: `git add .env.example`.

## 7. Командный сетап Claude Code (скиллы/агенты/настройки)
Теперь конфиг Claude Code едет в репозитории — сотрудник получает его при клоне:
- **Скиллы** (~36: SEO/контент/n8n/ui/council-review/mpstats/photo-editor) — контент в `.agents/skills/` (в git), разворачиваются в `.claude/skills/` командой `node scripts/setup-claude.mjs` (кросс-платформенно: симлинки на mac/linux, копии на Windows — поэтому симлинки не коммитим).
- **Агент** `studio-qa` (`.claude/agents/`), **dev-launch** (`.claude/launch.json`), **MCP** `virlo` (`.mcp.json`, токен через `${VIRLO_TOKEN}`).
- **Режим разрешений сотрудников** = `acceptEdits` (общий `.claude/settings.json`): авто-правки файлов, но команды/bash спрашивает — безопасно для новых людей. **Твой `bypassPermissions` перенесён в `.claude/settings.local.json`** (не коммитится) — твой режим не изменился.

Что НЕ шарится (личное/секреты/тяжёлое): `settings.local.json`, сессии/worktrees, `gstack` (~1 ГБ, ставится отдельно), Palmier (твоя подписка), computer-use/claude.ai-коннекторы, любые токены.

Опциональные токены (только если сотрудник будет ими пользоваться) — `MPSTATS_TOKEN` (скиллы mpstats/photo-editor), `VIRLO_TOKEN` (MCP virlo). Их кладут в окружение шелла; без них остальное работает.

## Проверить весь флоу
1. PR, меняющий только `.md`-файл (напр. правку в `docs/`) → ждёшь «✅ влил» в ТГ, PR смержен автоматически.
2. PR с правкой любого кода (`.ts/.tsx`) или `package.json`/`.env.example` → чек `ai-gate` красный, в ТГ «⚠️ проверь», влить можешь только ты (bypass).
3. Логи прогона — вкладка **Actions → ai-gate**.

## Когда сотрудник уходит
1. Settings → Collaborators → удалить. 2. Ротни секреты, которые были у него.

## Тонкости и риски (честно)
- **Авто-мёрж без человека** — только для доков/текста (allowlist). Весь код всегда проходит через тебя. На каждый авто-мёрж приходит ТГ-уведомление: если что — откатывай (revert PR).
- ИИ-ревью **не идеально** и нужно лишь как второй слой: жёсткая гарантия — это allowlist (код вообще не авто-мёржится) + branch protection. Дифф ассистенту подаётся как недоверенный ввод (анти prompt-injection).
- **`REVIEW_TOKEN` ≠ `CRON_SECRET`**: Action ходит в ревьюер отдельным узким токеном, мастер-`CRON_SECRET` в GitHub не попадает. При утечке `REVIEW_TOKEN` злоумышленник получает только ревью-эндпоинт, не весь director-cockpit. Всё равно держи его в секретах, не в коде.
- **Отдельная, пред-существующая дыра:** finance-panel `/api/*` на уровне приложения не авторизованы (`proxy.ts` их не гейтит) — защита только Vercel Deployment Protection. К гейту это не относится, но закрыть стоит; вынес отдельной задачей.
- Хочешь «одобрять прямо из Telegram кнопкой» для escalate-PR — скажу как добить, это +1 вебхук в director-cockpit.
