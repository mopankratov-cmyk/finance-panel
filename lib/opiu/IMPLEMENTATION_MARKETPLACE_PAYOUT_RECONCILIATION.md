# Сверка поступлений маркетплейсов: фактический объём этой задачи

## Что реализовано для Ozon

Поступление проходит три разных состояния:

1. `accrual` — расчётный прогноз по плану заказов и юнит-экономике;
2. `report_confirmed` — сумма подтверждена финансовым отчётом Ozon, но дата прихода в банк может оставаться расчётной;
3. `bank_received` — деньги найдены в фактическом платеже ДДС и связь подтверждена пользователем.

Система не считает начисления или итог операций Ozon фактом поступления в банк.

Каждый отчёт разделяется по ключу:

`marketplace + cabinetId + companyId + reportId + periodFrom + periodTo`.

Это позволяет хранить несколько кабинетов одной компании, несколько отчётов на одну дату, корректировки отчёта, частичные выплаты и один банковский платёж по нескольким отчётам без дублей.

Факт ДДС хранится в существующей записи таблицы `payments`. Подтверждение сверки добавляет к ней устойчивую ссылку на отчёт и не создаёт вторую строку с деньгами. Неоднозначные и частичные совпадения требуют ручного распределения. Уже проведённые платежи не переписываются прогнозом.

Если API Ozon недоступен, последний подтверждённый результат восстанавливается из календарных записей. Расчётный прогноз можно просматривать, но обновление календаря блокируется до восстановления подтверждённых данных.

Изменённые пользователем правила выплат сначала показываются как предварительный расчёт и применяются к календарю только после явного подтверждения.

## Что реализовано для Wildberries

В этой задаче Wildberries остаётся только честным расчётным прогнозом:

- исходный план заказов менеджера не изменяется;
- отклонение фактических заказов влияет только на финансовый прогноз после трёх последовательных дней;
- прогноз строится отдельно по выбранным кабинету и компании;
- глобальный старый план доступен только для просмотра и не записывается в календарь;
- правила выплат требуют явного подтверждения перед записью в календарь;
- данные из браузера или локальных настроек не выдаются за подтверждённую сумму финансового отчёта или факт банка.

Сверка финансовых отчётов WB с ДДС в эту задачу не входит и не заявляется реализованной. Для неё нужен отдельный PR с кабинетными идентификаторами отчётов, серверным API, устойчивыми связями с ДДС и самостоятельными тестами.

## Границы безопасности

- Рабочий или глобальный план нельзя записать в календарь без утверждённого плана конкретного кабинета.
- Расчётная дата никогда не подписывается как подтверждённая маркетплейсом.
- Запись календаря не создаётся при деградации источника отчётных данных Ozon.
- Повторная синхронизация не создаёт дубли.
- Распределение одного банковского платежа не может превышать сумму платежа.
- Сумма всех поступлений по отчёту не может превышать сумму отчёта.
- Изменения даты и суммы отчётной записи сохраняют предыдущие значения в истории комментария.
